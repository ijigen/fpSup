# 虛擬模式的壞點修正（v0.7.25test，2026-11-03，離線候選，未上機、未部署）

[驗] = 離線實跑或實測資料證實；[推] = 推論。背景見 `imx410-lab/notes/DEFECT_CORRECTION.md`。
證據與腳本：`validation/20261103-defect-virtual/`。

## 1. 問題

- [驗] 每次換模式時，`FUN_c030e2a0(ctx 0xC343A66C, mode, 1, 0, xlate 0)` 會把 R68 +04 指定的 flash 表**原樣**交給 DEFC。只有 v33 模式（102/108/124/152）和放大表內的模式會先平移。SensorLab 的 230/231 兩者都不是。
- [驗] core/smc 寫的 R68 列，對所有 SensorLab 配方都是 +04 = 97、+08 = 1、+0C = 0x61，+10..+2C 是正確的裁切窗與換算型別；這些欄位**只有換算時才會被讀**。所以 DEFC 拿到的是表 97，座標系是 mode 97 的光柵：
  - 1×1（TIM x0 = 16，表 97 原點 x = 8）：整張表錯開 8 px。8 是偶數，所以修的是**同色**的錯誤像素。
  - V2（12v2、14v2）：1×1 列座標直接套在合併後的列上，完全錯位。
- [驗] 量化（G7 暗場，BUFA0 在 DEFC 之前，`geometry.py cover`）：

| 配方 | 熱點 | 換算後的表覆蓋 | 原樣表 97 覆蓋（修正前 DEFC 拿到的） |
|---|---|---|---|
| 12v2 DC 6048×4040 → 3024×2014 | 466 | **98.3 %** | 0.6 % |
| 14v2 → 3024×2014 | 1333 | **97.4 %** | 0.5 % |
| 14-bit 1×1 key 0 → 3024×2020 | 871 | **97.8 %** | 0.8 %（平移 +8 px 才有 98.0 %） |

## 2. 做法

1. **commit**（UI 執行緒，`ap_busy()` 已在開頭擋掉錄影）：槽位 `valid = 1`、查表 hook 已能回應這個 id 之後，呼叫 `ap_defc_build`：
   - 先讀 R68 +08，0 就不做，照原廠規則；再讀 +0C（來源表 id）。
   - 從 `*0xC343A71C`（flash 缺陷緩衝）+0x16000 的目錄找出來源表：位址、字數、邊界（不可越過表尾的點清單區）。
   - 緊接在呼叫前再檢查一次 `ap_busy()`，然後呼叫韌體的 `FUN_c0310740(ctx, 我們的 id, 字數, A->dtab[n], A->defc[n].list, 來源表)`。R68 的裁切窗與型別、META 寬高，都由韌體經我們的查表 hook 讀到。
   - 輸出必須在緩衝內有 4×0xFFFF 結尾，`tbl` 才填入表的**非快取別名**（`p − SL_ALIAS`），之後做原本就有的整個 D-cache 清理。
   - 任一步失敗：`defc = 0`，DEFC 照原廠行為拿 c030e2a0 自己選的表。`defc_last` 記錄原因（見 ap.h）。
2. **hook H_DEFC @ 0xC030F624**（K_BL，原字 `0xFA0C99D5` = `blx FUN_c0635d80`）。條件：r0 == 2、r5 是我們有表的槽位 id → 把 r1 換成 `&A->defc[槽位]`（`{tbl, list[128]}`）；其他情況原樣往下。
3. **緩衝**：SensorLab 自己的，在 `struct ap` 尾端，每槽一份：表 0x4000 字（64 KB）＋ 0x204 B。AP_MEM_BYTES 0x16000 → 0x36000，sup block 從 ≈435 KB 變 566,784 B。槽位輪替：只寫目前沒有在跑的槽位，所以 DEFC 正在 DMA 讀的表不會被改寫。

### 和交辦設計不同的地方（讀碼證實）

- **不能掛在 `FUN_c0635d80` 入口**：它是 Thumb 函式，ap.c 的 K_ENTRY 會在入口寫 ARM 分支，行不通。[驗] 全映像掃描 ARM 與 Thumb 的 BL/BLX：它只有 6 個呼叫點，**全部在 ARM 函式 `c030e2a0` 裡**。改掛呼叫點 K_BL，沿用 H_BINK1/2 的寫法。
- **小格式單表的呼叫點是 0xC030F624，不是 0xC030EC94**：`C051F4D8() == 0` 會跳到 C030ECE0 那半。這是 unicorn 跑完整 c030e2a0 時抓到的；我第一版掛錯了。另外 5 個呼叫點是大格式／雙表的複本，以及兩個「關閉」呼叫（r0 = 0）。
- **模式取自 r5，不是 imager+4**：[驗] `c030e2a0` 在序言 `mov r5, r1` 之後，整個函式沒有其他指令寫 r5，所以 r5 就是這次載入的模式參數本身。
- **R68 不用補**：core 已經寫對（見上）；只檢查 +08 / +0C。

## 3. 驗證（離線）

`apply/test_apply.py DefectTests`（10 項），用 unicorn 跑真實韌體映像：

- [驗] **真實換算器 = Python 移植版**（`imx410-lab/offline/defect_tables.translate`），逐 u16 相同、點清單 128 字相同。5 個配方：12v2、14-bit 1×1、14v2、2×3（V1）、2×2。來源是相機自己的 flash 緩衝傾印（`captures/defect/flashbuf.bin`，表 0x61 = 14454 字）。
- [驗] **韌體自己的平移路徑算出同一張表**：`c030e2a0(…, xlate 1)`（>0.5 s 拍照路徑）對我們的 id 用 class 0 緩衝自己換算，結果和我們的逐位元組相同。
- [驗] 跑完整 `c030e2a0` → hook → Thumb `c0635d80` → `c0633778`，寫進映射的 DEFC 暫存器：
  - 我們的 id：`0x300F0D84 = (表 + 0xC0000000) >> 2`，點暫存器等於我們的清單。
  - 原廠 97/98/106/8/10：和沒有 hook 的參照**完全相同**。
  - 關閉呼叫照常關閉 DEFC。
- [驗] 快取別名：sup block 映射在 0xC… 別名時，交給 DEFC 的是 0x4… 位址，且兩個別名讀到的內容相同。
- [驗] 錄影安全：
  - 錄影中 commit：不換算、不配置。
  - commit 途中開始錄影：不會呼叫換算器（`defc_last = −4`）。
  - 錄影開始時的模式設定：只換指標，不配置、不換算。
  - 換算器的 class-10 暫存都在同一次呼叫內釋放。
- [驗] 退回原廠行為：緩衝未載入（−1）、目錄無效（−2）、沒有 0x61、表太大、會越過點清單區（−3）、暫存配置失敗（−5）。這幾種情況 DEFC 拿到的都和原廠相同。
- [驗] 輪替：第二次 commit 不改寫前一個槽位的表，兩個 id 各自載入自己的表。
- [驗] G7 熱點覆蓋：見 §1 的表（`hot_g7.json`，測試門檻 > 95 % 且原樣表 < 20 %）。
- [驗] 負向對照：
  - 修改前的 ap.c（`validation/…/pre-change/`）讓我們的 id 載入原樣表 97，`test_negative_control…` 證實。
  - 新測試套在修改前的程式碼上，9 項失敗（`negative_control.txt`）。
- [驗] 突變：11 個 DefectTests 突變全部被抓到。r0 == 2 檢查、點清單預填在可到達的輸入上等價，保留為防護。

**沒有驗證到的**

- DEFC 硬體實際讀這張表的效果。
- 「DEFC 在 RWZM 之前」[推]：DEFC 在前端；DNG 在 DEFC 之後，這點 DEFECT_CORRECTION 有實測。
- 換算器在相機上的耗時。
- 第 1 幀錯一列的格式（FIRST_FRAME_PURPLE）：該幀的修正位置也會錯一列 [推]。

**真實 DNG 不能當證據**：`20261103-first-frame-purple` 是有光的場景、短曝光。在預測的壞點位置上，殘差平均是 −0.007 / −0.001，隨機位置是 +0.013 / −0.013，任何平移下都沒有訊號（`dng_null.json`）。「跨片段位置相同的離群點」大多是靜止場景的紋理：同一位置在三段裡都出現，形狀是邊緣，不是單點。原廠 FHD 因為 3:1 縮放比較平滑，所以看不到。要驗證只能用暗場。

## 4. 上機測試計畫（Bei 同意後）

1. 部署 v0.7.25test（只換 SensorLab BIN）、重開，蓋上鏡頭蓋。套用 12v2 DC 6048×4040 → 3024×2014。
2. `sq_test 17` 讀 `ap_status`：`defc = 1`、`defc_last = 1`、`defc_builds ≥ 1`；LV 重載後 `defc_loads` 會增加。
3. `mem get 0x300F0D84`，應等於 `(A->dtab[cur] 的 0x4… 位址 − 0x40000000) >> 2`；切回原廠 106 時應回到 flash 表 97 的位址。
4. 暗場錄影，方法同 DEFECT_CORRECTION「錄出的 DNG 在 DEFC 之後」：IMXB 代換 SHS = 4、30 dB（`003D..0040` = 3965）、LCG，錄 2 s。三組各一段：
   - (a) v0.7.25test 開啟；
   - (b) 同一版加 `imager defect_collect_off 1`（DEFC 關閉）；
   - (c) v0.7.24test（原樣表 97）。

   比較第 2、3 幀都穩定的熱點：預期 (a) ≪ (b) ≈ (c)。也要對 14-bit 1×1 key 0 做一次（(c) 應該也和 (b) 差不多，因為只是錯開 8 px）。
5. 原廠 106 暗場一段：熱點數和修改前相同，`defc_loads` 不變。
6. 錄影開始／停止各 3 次，不可凍結；觀察 `commit_us` 增加多少（換算器耗時）。
