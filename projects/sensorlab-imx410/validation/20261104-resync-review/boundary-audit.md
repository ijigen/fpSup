## 同一幀：completion、writer 與 DNG 確實對得上

共 **16 個有 trace 的 take、64 組 done/write 配對**：

- 64/64 的 done 與 write raster 物理位址一致，採樣有效旗標都為 1。
- 64/64 的四塊採樣位元組一致。這四塊合計 **160 bytes**：row 0 開頭 32 B、row 0 尾端 64 B、row 1 開頭 32 B、最後一行尾端 32 B。
- 16/16 take 的第一個 done 採樣，亦與該 take 第一張 DNG 的上述四個**對應位置**逐 byte 相同。
- 11 段異常首幀：row 0 尾端 64 B 在 arm、done、write 及 DNG 都是同一個本次 xorshift 標記。5 段正常首幀：done 時這 64 B 已被覆蓋。16/16 與獨立 DNG dy 分類一致。
- 所有 take 第 2～4 幀的 done/write 都沒有保留該首幀標記。標記只種在首個目的緩衝區，這不等於第 2～4 幀也做過「預先種標記」試驗。

因此，**首幀 row 0 尾端在最早的已記錄完成回呼就仍未被影像覆蓋**；後續到 writer 與檔案沒有把這四處採樣改壞。這補上先前研究尚欠缺的 live completion 邊界。

不可擴張成「已核對全幀在交接過程完全不變」或「整個 row 0 沒有任何寫入」：只比較四塊固定採樣，且異常 row 0 的開頭確實可能已被碎片覆寫。`head1` 是 row 1 開頭，不能把它誤當 row 0 的有效影像起點。整張位移另由 DNG 中央區域對位確認；這份 trace 本身不是 sensor 輸出線路的量測。

## `r2280` 為下一個緩衝區，不是 callback 搞錯位址

done 採樣時，`r2280` 需先 `<<2` 並轉成 uncached alias 才能與 raster 比較。結果：

- 與當次 callback raster：**0/64 相同**。
- 與下一次 done 的 callback raster：有下一筆可比的 **48/48 相同**。

因此不能用 `r2280 != ras` 指控當次記錯 buffer。callback 傳入的完成位址與 writer、DNG 能完整對上；live 目的暫存器此時已是下一個目的地。

原廠 `FUN_c0630d60 @ C0630D60`（`out/decomp/full/blk_c06.c:43977`）也不是永遠直接把當下 `30182280` 交給 callback：它包含軟體雙緩衝 shadow 路徑，透過 `FUN_c0630b78` 取完成位址。trace 沒記錄該 branch guard，所以不能僅由本次資料斷言是哪個指令更新了暫存器；「snapshot 指向下一個 buffer」本身有 48 次直接對應證據。

## Sensor restart 至 arm：比舊推論晚很多

這次可比較的 clock 來源為：

- bus logger：`projects/imx410-lab/buslog/buslog.S:53` 定義 `TICK_US=C002B6E0`，`:191–199` 在記錄 sensor writer 入口時讀取；這是命令時間，不是 sensor 收到／鎖存完成時間。
- arm task：`apply/ap.c:54` 與 `:376` 使用相同 `C002B6E0`，trace `us` 欄位記錄該值。本分析用這個 task `us` 減每段第一個 `0011=01` 的 bus `t`，不依賴 IRQ 的近似時間換算。
- IRQ done：由 epoch 與 timer raw 推算，缺少 pending-bit 修正，epoch 邊界仍可能有 ±1 s 誤差。arm 的同源 task `us` 和近似時間相差 8–24 µs；本批首個 arm→done 差值均合理且無 1 s 跳躍，但不把這個檢查當作完整硬體時鐘驗證。

| 資料 | `0011=01` → arm（同源 task clock） | arm → done 1（IRQ 近似 clock） |
|---|---|---|
| 27，五段 12h2 | 472.494–473.162 ms | 53.388–54.041 ms |
| 28，十段 12v2 | 472.444–506.057 ms | 40.827–41.497 ms |
| 29，t01 | 806.171 ms | 41.443 ms |

這推翻舊筆記由 bus 支線推得的「137–168 ms、約第 4–5 個 sensor frame 時才 arm」。若以 29.97 fps 換算，472 ms 約 14 個週期，但**仍不能宣稱已測出真正的第 14 個 sensor frame**：沒有接到 sensor 的 frame ID／實體輸出邊界，而且 `0011` pulse 的確切硬體語義不是由時間戳證明。

同理，29 相對 28 的首段 timestamp 差不能全部歸因於約 63 ms 的 resync；不同 take 的前置流程可能不同。可以確定的是，新增 pause/resume 在 mode switch 後確實發生，而第一個被存下的壞幀並非緊貼該 `0011` 命令。

## 可採用的結論

「後段 writer 把完整首幀改壞」已不是這批資料支持的方向：首列尾端未覆蓋的標記在完成回呼時就存在，而且同幀採樣一路吻合。實際執行的原廠 pause/resume/resync 也沒有消除異常。接下來應保留擷取端 sensor／接收器／裁切／DMA 的界線，使用已可解碼的 TG 採樣協助定位；不能再把原始大整數當作無用計數，也不能把八次失敗擴張為所有 sensor 啟動狀態都已排除。
