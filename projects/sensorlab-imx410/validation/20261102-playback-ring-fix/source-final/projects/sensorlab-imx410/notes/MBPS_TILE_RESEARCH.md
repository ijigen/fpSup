# SensorLab-IMX410：MB/s 格子的研究（未壓縮、lossless 預測、媒體門檻）

2026-10-29，離線研究：沒碰相機、沒改原始碼。
標記：[量] = 卡上真實檔案的位元組數或上機紀錄；[模] = 用驗證過的 LJ92 模擬器算未壓縮幀（見 §2.1）；
[C] = 反編譯讀到；[推] = 推論，待驗。

## 0. 結論

- **大字（未壓縮）**：`MB/s = fps × (W×H×b/8 + 79 184) / 1e6`，`b = AD≤12 ? 12 : 14`。
  CinemaDNG 每幀有 **79 184 B 檔頭**（FHD 2.4%、1008×672 7.2%、6K 0.6%）[量]；像素區本身沒有列補白。
  FHD 12-bit 29.97p = 97.2 MB/s，跟 STORAGE_SPEED §3 的實測一致。
- **小字（lossless 預測）**：每像素位元數 `B = min(b, 4.7 + 0.5·log2(ISO/100) + (b−12) + 1.5·[1×1])`，
  加上壓縮幀的固定開銷，再依引擎吞吐量算出「來不及壓、照原樣寫」的比例（§3）。
  36 個資料點**沒有一個超過預測值**（最小餘量 +0.6%）。曝光正確、有紋理的畫面貼近上緣；
  室內偏暗的實拍中位數會**高估約一倍**。
- **著色**：比較的是「媒體實際要寫的量」，也就是每檔補齊到 cluster 之後的大小，再加上每檔的固定成本（§5）。
  **錄影媒體可以在錄影前讀到**：MediaSelect 加 SSD 驅動的就緒位元組 [C]；
  SD 的匯流排模式（Normal / UHS-I / UHS-II）也讀得到 [C]。兩者都還沒上機驗證。

## 1. 未壓縮幀：檔頭與補白

所有 `Compression=1` 的 CinemaDNG（卡上檔案，排除工作樹的重複複本）[量]：

| 尺寸 / 位元 | 幀數 | 檔案 − W×H×b/8 |
|---|---|---|
| 1936×1090 12b | 3 396 | **79 184**（另有 51 幀 78 860、5 幀 80 208） |
| 1936×1090 10b | 32 | 78 860 |
| 1936×1090 8b | 8 | 79 880（多一張 256 筆的 LinearizationTable） |
| 3856×2170 12b | 2 | 80 272 |
| 3872×2182 12b | 2 | 79 328 |
| 2016×1344 12b | 937 | 78 848 |
| 1008×672 12b | 96 | 79 104 |
| 3024×2010 12b（OG3K 舊版建置） | 13 | 182 640（舊 OG 的檔頭比較大） |

- 像素區正好等於 `W×H×b/8`，有時多出 8 或 12 B 的尾巴。**檔頭約 79 KB 是唯一值得算的開銷。**
  格子用 79 184 即可；要保守的話用 80 KiB。
- 11-bit AD 錄成 12-bit：未壓縮一律算 12 bit。
- **媒體上還有 cluster 補齊**：每檔補到 cluster 的整數倍（相機格式化時，SD ≤128 GiB 的 cluster 是 128 KiB，
  SSD 1 TB 是 512 KiB，見 research/storage/notes/FORMAT_CLUSTER_SIZE.md）。WRITER_THEORY 用 rec log 擬合，
  發現補齊的部分**有傳到媒體**（SSD 240p 的模型值 253 MB/s，實測約 250）[量+推]。
  這部分不算進大字，但著色時要算進去（§5）。

## 2. 壓縮率的資料

### 2.1 先證明可以用模擬補資料

fp 的 lossless 輸出是標準 LJ92：SOF3、每個 tile 2 個分量（偶數欄和奇數欄交錯，也就是同色相鄰）、
**predictor 1（左鄰）**、Pt=0，**每個 tile 一組自適應 Huffman 表**（`FFC4` 每格不同）[量，A001_044 f2 解析]。
第一欄用上方預測，第一列第一點用 2^(P−1)，所以每張表都有一個類別 11 的符號。
Byte stuffing 很少：0.92 MB 只有 139 個 `FF00`。每個 tile 的 JPEG 檔頭約 70–80 B。
壓縮後的檔頭是 79 872 B，整個 payload 補白到 1 KiB 的倍數（codec_job.h）。

用這套規則寫了一個估算器：每個 tile、每個分量各自做最佳 Huffman，再加上類別位元。
拿它去算**相機自己壓縮的幀**（先用 rawpy 解開，再重新估算），跟實際的 TileByteCounts 比：

| 範圍 | 幀數 | 誤差 |
|---|---|---|
| FHD 512×368、OG3K 512×512、1008×672 512×336（相機編碼） | 約 60 | **+0.0% 到 +0.7%**（只會高估） |
| OG3K 512×368 舊版切法（高度 2010 補到 2208） | 4 | +5%（補白區相機編得比較省；方向是保守的） |

所以下面標 [模] 的數字，誤差可以視為 < 1%（往高估的方向）。
估算器在 scratchpad 的 `lj92est.py`（`dngscan.py`、`dng_est.py`、`bins_est.py`、`fit.py`、`rate.py` 都在同一個目錄），
不在 repo 裡。要留就搬進 `projects/sensorlab-imx410/tools/`。

### 2.3 同一場景的相對效應（imx410-lab `captures/bins`，BUFA 讀出，增益不明）[模]

| 讀出 | 尺寸 | bpp | 時間雜訊 σ（DN） |
|---|---|---|---|
| m10 1×1 | 6064×2062 | **7.17** | 6.3 |
| vbin2 / vbin3（只垂直） | 6064×1500 / 1000 | 5.51 / 5.49 | 4.2 |
| m98 2×2 / m58 2×2fast | 3016×1500 | 5.61 / 3.64 | 4.2 |
| m139 3×3 / m140 3×6 | 2008×1000 / 500 | 5.70 / 5.80 | 3.2 |
| vbin2 14-bit | 6064×1500 | 8.18（截成 12-bit 是 6.14） | 24 |

- **位元深度**：14→12 是 **+2.04 bit**（同一幀截位）。原理：雜訊主導時，多 1 個 LSB 就多 1 bit。
  另有 10-bit 原生錄影：同一場景是 2.60 vs 12-bit 的 2.76，暗場下只省 0.16 bit。
- **11-bit AD 錄在 12-bit 容器**：把 12-bit 幀最低位清零來模擬，只省 0.00–0.14 bit。
  清兩位（模擬 10-bit）省 0.27–0.36。**AD 11 不給折扣**（保守）[模，截位不等於真的 11-bit AD]。
- **合併**：1×1 比 2×2、3×3 多約 **1.5 bit**；2×2 與 3×3 幾乎一樣。
  6K 靜態照（1×1，14b）扣掉 2 bit 之後，比 FHD 同 ISO 多 0.3–0.5 bit。公式用 +1.5（保守）。
  fast 模式（m58、m8fast）低很多，因為讀出裡含黑行（p1=0），這不是壓縮率的差別。
- **縮放（RWZM / ISP bin）**：UHD（1×1 再縮）實測只有 2.6–2.7，比 FHD 還低。
  原理上縮放會平均雜訊，所以**不給額外懲罰**；也不給折扣，因為資料點只有兩個場景。
- **ISO / 亮度**：真正決定 bpp 的是「殘差的雜訊（DN）」。σ² = 讀出雜訊² + g·S，g 跟 ISO 成正比。
  S 固定時，每升一檔 ISO，σ 乘 √2，**bpp +0.5**。這就是公式的 ISO 項。
  暗場只有讀出雜訊：ISO2500 是 σ 1.05、2.98 bpp；ISO6400 是 σ 3.15、4.73 bpp。
  σ 每翻倍約 +1 bit，跟高斯熵 `log2σ + 2.05` 吻合。
- **全白過曝**：1.04 bpp（og3k120-defect，飽和 4095）。過曝只會更小。

## 3. 公式（相機上用 C 算）

輸入：錄影尺寸 W×H、AD、sensor mh×mv、ISP hb×vb、fps、ISO（拿不到就用 3200，見 §6）。

```
b      = (AD <= 12) ? 12 : 14
u      = (mh*mv == 1 && hb*vb == 1 && 沒有縮放) ? 1 : 0       // 1×1 原生讀出
B      = min(b, 4.7 + 0.5*log2(max(ISO,100)/100) + (b-12) + 1.5*u)   // bit/px
F_u    = W*H*b/8 + 79184                                      // 未壓縮檔
grid   = 原廠規則：tile 寬 32..512（32 的倍數）、高 16..512（16 的倍數）、≤160 格，
         取 補白面積 + 32250×格數 最小者（tile_grid.h，FPL_TILE_PIXELS）
F_c    = min(F_u, W*H*B/8 + 80*tiles + 79872 + 1024)          // 壓縮檔；不比較小就寫原幀
t_c_ms = 4.7*補白Mpx + 0.00046*(欄數*補白高) + 2.0            // 引擎每幀時間（TILE_GRID 聯合擬合）
p_raw  = max(0, 1 - 1000/(fps*t_c_ms))                        // 來不及壓的幀比例
小字   = fps*((1-p_raw)*F_c + p_raw*F_u)/1e6
```

整數寫法（相機沒有 libgcc）：B 以 1/16 bit 為單位，
`B16 = 75 + 8·ev3/3 + 32·(b==14) + 24·u`，其中 `ev3 = round(3·log2(ISO/100))` 是 1/3 檔數
（ISO 本來就是 1/3 檔一階，可以查表）；最後 `B16 = min(B16, 16·b)`。

- **p_raw 有實測**（TILE_GRID，OG3K 29.97p，7 種切法）：
  實測沒壓縮的比例 14.4 / 20.8 / 23.0 / 28.9 / 41.0 / 7.9%，
  `1 − 33.37/t` 算出來是 13.7 / 20.5 / 22.7 / 28.5 / 40.9 / 6.5%。誤差 ≤ 1.4 個百分點 [量]。
  t_c 的聯合式在 OG3K 512×512 算出 37.2 ms，實測 35.7；FHD 512×368 算出 14.7，實測擬合 13.7。兩者都偏高，方向保守。
- 常數 4.7 由「曝光接近中灰的 ISO3200」那個點反推（7.16 − 2.5）。
  ISO100 那端是另外獨立量的（最高 4.48），兩端都符合每檔 +0.5，所以 ISO 項不是硬湊出來的。

## 4. 錄影媒體與 SD 模式（相機上怎麼讀）

都是靜態讀出 [C]，沒上機。

**錄影媒體是 SD 還是 SSD**（錄影前就讀得到）：
- MediaSelect 的值：`fac = *(u32*)0xC31CAA80`；`item = fac->vt[0x354](fac)`；
  `v = FUN_c006d530(item, FUN_c00913f8(item, 0xFFFF, item->vt[0x1C](item), 0x80000001))`。
  **0 = SD，1 = USB SSD**。依據：`MenuItemMediaWriteMode::v3`（C00AB8E8）寫 `settings+0x9C = (v==0) ? 1 : (WriteMode==1)`，
  也就是「SD 永遠聚合」，跟 MEDIA_WRITE_MODE.md 的結論一致。WriteMode 自己是 `param_1`，+0x354 那一項是 MediaSelect。
- SSD 就緒：`FUN_c0518410(5)` = `*(u8*)(FUN_c0366a98(5) + 0x1C)`。
- 原廠格率選單（`MenuItemMovieFrameRate::v8` C00A84E0）就是用「SSD 就緒 && MediaSelect==1」來決定 SSD 格率上限。
  **格子照抄同一個判斷即可。** RES-Custom 的 frmax 也走這條（test_rcd_bitdepth 模擬過 C0518410、+0x354）。

**SD 的匯流排模式**：
- `drv = FUN_c0366a98(1)`；`mode = (*(drv->[+0x18] + 0x24))(drv)`：
  0 = 無效、**1 = Normal、2 = UHS-I、3 = UHS-II**。
  依據：shell `sdcard` 的 FUN_c040AD00（印出 Normal SDCARD / UHS-I / UHS-II），
  以及 rec log 的 `Normal()` C06AFDD0（rec log 的第二行就是它印的）。
- SSD：同一張 vtable 的 `+0x28` 回傳鏈路的 Mbps（rec log 在 slot 5 時印 `%dMbps`）。
- ⚠ `FUN_c0366a98(slot)` 的 slot 只能是 1、2、3、5，其他值會進無窮迴圈的 assert。
- 錄影中的 slot 在 `0xC38D2B5C`（rec log 用）。只有 rec log 啟動時才會寫，錄影前不能拿來判斷。
- 容量（決定 cluster）：同一張 vtable 的 `+0x1C(drv, idx, &out)`，rec log 用 idx 0/1/2/4 印 size/free。
  cluster = 卷物件的 `+0x146C`（每 cluster 磁區數）× `+0x1460`（磁區位元組）。卷物件的位址還沒找到。

## 5. 媒體門檻（保守）

不要只用一個 MB/s 數字。每個檔要先補齊到 cluster，還有固定的 CPU 成本。所以用工作比判斷：

```
duty = fps × ( ceil(F/C)·C / R  +  0.00051 s )      F = 每檔位元組（大字用 F_u，lossless 用 F_c 加權）
綠   duty ≤ 0.75      黃 0.75–1.0      紅 > 1.0          （只要一種顏色的話：duty > 0.85 就著色）
```

| 媒體 | R（傳輸） | 依據 | C（相機格式化） |
|---|---|---|---|
| SSD（USB 5 Gbps） | **390**（擬合 412） | `sdcard test3` 390 [量]；rec log 43×1 572 864 B / 164 ms = 412 [量] | 1 TB 512 KiB、≤512 GiB 256 KiB |
| SD UHS-II | **240** | 正常批次 240–280 MB/s（early-dng-handoff、STOP_HANG 241）[量] | ≤128 GiB 128 KiB、≤512 GiB 256 KiB |
| SD UHS-I | **87** | 同一張卡退回 UHS-I 時 87 [量]；SDR104 上限 104 | 同上 |
| SD Normal | 20 [推] | HS 匯流排 50 MB/s 的一半 | 同上 |

c_f = 0.51 ms/檔（SSD 批間空檔擬合，WRITER_THEORY）。SD 的中繼資料 I/O 已確認是 0。

拿已知結果檢查：
- SSD M12 240p：1 095 248 B 補到 3×512 KiB → duty 1.04，**紅**。實測確實積壓，第 94 幀停錄 ✓
- SSD FHD 60p：duty 0.57，綠 ✓
- SD UHS-II M12 120p：duty 0.65，綠。實測 131 MB/s 可以持續 ✓
- SD UHS-I M12 120p：duty 1.7，紅。實測 87 MB/s 積壓 ✓
- SD UHS-II FHD 60p 未壓縮：duty 0.88，黃。主力卡錄得下（WRITER_THEORY 原廠 202 vs 需求 194），
  另一張 V60 卡在 134 幀時以 vbuf 自停 ✓（剛好落在黃區）
- 錄影 RAM 緩衝約 600–750 MB（STORAGE_SPEED §4）。紅區也能錄幾秒，但遲早會停。

⚠ SD 的 R **跟卡有關**。同一張卡可能協商成 UHS-I 或 UHS-II；
`sdcard test3` 的 94 MB/s 是單次 50 MB 寫入的延遲限制，**不是**錄影時的持續速率。

4. 1×1 的 +1.5 bit 來自 imx410-lab 一個場景（增益不明）。需要 1×1 FHD 大小、已知 ISO 的錄影來確認。
