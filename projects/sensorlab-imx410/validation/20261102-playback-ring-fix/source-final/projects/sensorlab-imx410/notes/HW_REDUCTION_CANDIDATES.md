## 2. HSEP 重新檢查(Bei 覺得「2×/3× 怪怪的」,你是對的)

我重新讀了 32 + 7 個 case 的 `input-u16le.bin` 與 `analysis.json`。

**模式對位元**:`c0131410` 寫的是 `0x302109A4` 的 bits[1:0](`blk_c01.c:33487–33497`),同時清掉 bit16,
另外改寫 `0x302109B0`(水平範圍)與 PRE_TOP_LM `0x302109C8` 的高半字。

| 位元 | harness 的名稱 | 實際運算(packed14、endian 1) | 鑑別證據 |
|---|---|---|---|
| `00` | mode0 | `out = (((a>>2) + (b>>2)) / 2) << 2`,a、b 是同色相鄰兩點(x、x+2) | 脈衝 10000 → 5000(排除抽點);斜坡：只在輸出端截位的模型有 96 點不符，必須先在輸入端截 |
| `01` | mode1 | `out = min((a>>2) + (b>>2), 4095) << 2` | 斜坡 x = 1 輸出 0(若輸入不截應為 4);CFA 8192 + 8193 → **16380**,也就是 12-bit 飽和 |
| `10` | mode2(÷3) | 三欄一組 `[3k, 3k+1, 3k+2]`,取首尾平均：`R G R → avg(R,R)`、`G R G → avg(G,G)` | 脈衝在 x = 0 或 2 → 6000;x = 1 → 沒有輸出;x = 4 被略過 |
| `11` | — | 原廠 setter 的分支互斥，不會產生這個值;**沒有測過** | — |

**掉了什麼、掉在哪裡**

- **輸入端**:每個樣本的最低 2 位在運算之前就沒了。
  - u16 輸入(enum 2)時，100…107 全部變成 96,也就是丟掉 4 位。
  - 兩種容器的共同點是「只留容器名目寬度的最高 12 位」。所以這條路由內部是 MSB 對齊的 12-bit 資料路徑 [推，強]。
- **輸出端**:結果 `<<2`,永遠是 4 的倍數。
- **相加模式**:在 12-bit 域飽和(4095)。每點平均超過約 8190 DN14 就會裁頂，所以它不是「15-bit 和」。
- **÷3 模式**:每色只用 3 個樣本中的 2 個(R 丟 x = 4、G 丟 x = 1)。
  雜訊只降 √2,不是 √3。這跟感光元件 vbin3「三列只用兩列」是同一種設計。
  輸出樣本的中心是 1, 4, 7, 10…,間距均勻。
- **bypass 不是 HSEP 的 14-bit 證據**:
  - bypass(`+0x47 = +0x48 = 0`)不加 sequencer feature bit `0x8`。
  - `c018cea0` 給它另一個路由字(`shadow 0x30240030` bit0)。
  - 所以 bypass 證明的是「SIG 的 RDMA/WDMA 能搬 RAW14」,不是「HSEP 能算 14」。
- **用途也對得上**:原廠唯一的直接 caller 是 `XC_SigproRawMakePreview`(`c04321a0`),它用 `00` 並自己選 12-bit 輸出。
  HSEP 是做 RAW 預覽縮圖用的，12 bit 很合理 [推]。

**結論**:目前的 HSEP 不是真 14 路線。剩下的開放項，只有未用過的控制位元：`11` 模式、`0x302109A4` 的 bit2–15、`9A8–9C4`。
沒有任何證據顯示其中有精度開關 [未]。

### A. 方法與來源

區塊清單由四個來源取聯集，再互相對照：

1. **韌體自己的區塊目錄** `FUN_c01597b8`（dump 函式）：用 capstone 逐指令追 `movw/movt`，
   取出每次 `FUN_c01f57f4(名字)` 之後的 `FUN_c015c1d8(start,end)`。結果：**479 段範圍、123 個名字** [驗]。
2. **shadow → MMIO 描述子表** `FUN_c019c810`：**193 個視窗**全部取出（不是只有具名的）[驗]。
   - 0x3011xxxx、0x3013xxxx、0x301Axxxx 的視窗全部落在 dump 名字的範圍內；
   - 例外只有 `0x30110470`（1 字，SLEEP 附近）與 **`0x30183000–0x301837FF` 的 21 個視窗**。
     後者是 SIG 自己的 RDMA/WDMA 通道組，dump 沒列（dump 的 BUF-A 只到 `0x301810C0`）。
   - bank 表 `DAT_c07d4360 = {0, 0x30000, 0, 0}`：`0x3024–0x3026` 是第二組 shadow，不是另一組硬體。
3. **常數位址掃描**：掃 `out/decomp/full/*.c` 全部 47,155 個函式裡的 `0x30xxxxxx` / `DAT_30xxxxxx`，
   以 4 KiB 分群，共 **91 個 4 KiB 頁**，每頁列出引用的函式。
4. **其他表**：
   - `C0189440` 不是每區塊的時脈表，而是 SIG ch0 時脈閘門那條指令（HIGH_FRAME_RATE_PATH §2）。
   - 每個 IP 的致能／IRQ 位元在 `0x3000B080..B440`（`b1d0` = COPY、`b130/b410` = SIG、`b0e0` = CRCT/RX 等），只部分對上，見 D。
   - DMA 通道：BUF-A 寫入（`0x30182000/2100/2200/2300`）、SIG 通道（`0x30183xxx`，設定器 `c014aa70/bf80/d2f8/daa8/e760/ee38` 六個）、
     BUF-D、BUFEF1/2、COPY、RDMA、SIES、無損、codec、顯示、NAND、SD 都已列入。
   - SoC 區塊名字串：除了 dump 那 123 個以外，沒有其他區塊名表。

**「縮小」的判準**：區塊有寬、高、比例、pitch、跳列、相位或抽頭欄位，**而且有韌體程式算出跟輸入不同的輸出尺寸**。
SIG 記憶體工作共 **52 個入口**（`c018cea0` 的呼叫者）。全部掃過「比例／除法」運算式，
找到的只有三種：
- ZOOM 的 `((in-1)*0x2000)/(out-1)`（`c0148f08/c01491e0/c01494e0`，以及 `c0163a98`、`c016d6d0`、`c01ddb58` 等工作）；
- HSEP 的寬度（`c0131410`）；
- RAWOUT 的欄窗（`c0156b90`，例：`c013cae8` 用寬度 /2 切左右半）。

沒有其他 SIG 單元有計算輸出尺寸的程式。

### C. 新評估的重點

1. **SIG 的 RAW 域濾波（31 個 N）**：結論「不能縮減」是結構性推論 [推]，不是逐位元欄讀過：
   - 52 個 SIG 工作裡，會讓輸出 DMA 尺寸跟輸入不同的只有 HSEP 旗標、ZOOM 比例、RAWOUT 欄窗。
   - 這 31 個單元的設定器沒有一個會被拿去改輸出尺寸。
   - 但如果某個單元有沒用過的縮減位元，這個方法看不到。
2. **SIG DMA 通道（`0x30183xxx`）**：
   - `c014aa70` 的描述子有 **22 個逐列位址**（`0x302200A4..F8`）、以 128 B 為單位的 pitch（`(x & 0x1FFFFF) >> 7`）、14-bit 寬與 10-bit 列數。
   - 沒有比例或抽頭欄位。所以它跟 COPY 同一類，只能靠定址做「整列」抽取或交錯。
   - 這補強了 P2 的「RawMix 加上 pitch 技巧」，但它本身不是新的運算硬體。
   - **pitch 只能是 128 B 的倍數**：P2 的 V÷2 設計要照這個條件排列寬。
3. **只有描述、沒有任何韌體寫入的單元**：RAW ZOOM（已知）、**BEIS**、HDR_HIST、YUV_PACK 的 `e130/e1b0`。
   - BEIS 的名字像 EIS（電子防手震）。如果它是 Bayer 域的幾何引擎，理論上可以重取樣。
   - 但它沒有 setter 可以模仿，依本文開頭的規則不直接掃未知位元。
4. **c013cae8**：另一個雙 RAW 輸入、經 SIG1 RAWOUT 輸出的工作（由 `XC_StillCreateYuv` 呼叫）。
   - 可用 `param[10]` 切成整幅、左半或右半，是分塊用的裁切，不是縮減。
   - 它是 RawMix 以外第二個「RAW 進、RAW 出」的原生工作，可以當 RawMix 測試的對照。

### F. 新候選

**沒有找到新的、有真 14 證據的縮減硬體。** 可以列入的只有：

1. **BEIS**（U）：唯一一個「可能是 Bayer 域幾何引擎、但完全沒用過」的單元。
   要它先得找到語意，例如其他用同一顆 SoC（Xacti `w71c1`）的機種韌體有沒有寫它。
2. **SIG DMA 的逐列位址表**：P2 RawMix 的抽取步驟可以不靠 COPY，直接在 SIG 通道內完成（列級）。
   精度仍待 §4.1。
3. **感光元件 PDAF-6C 欄參與控制**：在 14-bit AD 下測水平加法能不能活。
   這是感光元件端唯一沒排除、而且已知有作用的水平相關族。

### G. 判定

**對「韌體會驅動的硬體」來說，區塊層級已經查遍。** 154 個區塊每個都有歸類，三個來源互相對過，沒有遺漏的頁。

**但這還不是完整證明，剩下三個缺口：**

1. **欄位層級**：31 個 SIG RAW 濾波和 CRCT 的非縮放子區，只用結構推論排除。
   如果某個單元有沒文件、沒用過的縮減位元，這個方法看不到。
   → 補法：用現有 HSEP companion 的作法，逐一打開單元、餵斜坡圖，確認輸出尺寸等於輸入。這是低風險的待機測試。
2. **沒有寫入者的單元**：BEIS、RAW ZOOM、HDR_HIST。
   → 補法：先找語意來源（同 SoC 其他機種的韌體、SDK 字串），沒有語意就不掃。
3. **韌體從不碰的位址**：64 KiB 窗 `0x3003`、`0x3007`、`0x3009`、`0x3012`、`0x301C–0x301E`、`0x3029`、`0x302C`、`0x302E–0x3039`、`0x303B` 以上。
   - 這裡可能有晶片上存在、但這份韌體沒驅動的 IP。
   - 補法 (a) 已完成有限離線追查：`C012EE18` 的8個主IRQ加 `C01A5368` 轉註冊的IRQ23，
     都對到已知SIGSEQ、JPEG/JPEG2、SIES、BUFA、BUFD/SIG DMA、HDR及AE/AF統計，未新增RAW scaler候選。
     `C30000AC[n]` 是RTOS低階表；TA_HLNG=1時放共同wrapper `C0000E64`，真正C handler在
     `C30004AC[n]`（`out/decomp/full/blk_c00.c:661`）。未對上者需追consumer/MMIO，也可能是同步或共用IRQ，
     不能直接推成新引擎。本輪沒讀執行中RAM表，也不排除未被這組註冊引用的硬體。
   - 補法 (b)：唯讀探測這些窗。要先確認讀未對映位址不會造成匯流排錯誤，而且需要 Bei 同意。

另外，感光元件端還有 D 節列的四項沒在 14-bit 下試過；SUBCPU1 是不是真的存在也沒驗證（若存在，只是另一個 CPU 路線，不是縮減硬體）。

### 後續補充：原生 active H1 入口與原地 packed14 模型

本輪發現 `C017E138` 的 route0x10 會選H1 mux3、開BufA7 gate，與前述只查 `C0325228` 的範圍不同。
兩筆核×三路由共6個原ROM設定案例通過；仍沒有H1像素／精度或端到端RAW14證據。
CPU另有H2/H3原地packed14純量模型，驗證來源／目的packing、同色平均、緊密壓縮及guard，沒有測速。
