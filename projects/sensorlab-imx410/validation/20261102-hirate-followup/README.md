# v0.7.12test：高速預覽共用錄影取樣點，待實機測試

## 回報與重建

使用者實測 v0.7.11：「沒什麼變化，還是會卡住」；停止錄影後恢復。設定約 200 fps、38 MB/s、S16、0.3K；補充「12b 3x6 2x6 11b 3x6 都試過，都一樣，res 320x196」。是否仍持續寫出完整影片未知。本輪未操作相機、USB、daemon、卡或批次 runner。

QS `visible()` 顯示有效尺寸，預設 S16／0.3K 的錄影矩陣 336×206 扣去 16×10 邊距即 320×196。12b／11b 3×6 可依此重建，皆為 E1 獨立預覽路徑；2×6 未在同組 DC／RES 清單重建，保留為未核對，不代換其他配方。

v0.7.11 補齊 +B0 的資料傳遞成立，但本次使用者回報已否定其足以修復症狀。前輪凍結資料保留，產品說明更新為實測仍卡住。

## 候選與範圍

參考 `res-lab/validation/20261014-unified-hirate/RESULTS.md`：歷史 r10／240p 錄影取樣預覽曾由使用者確認 LCD 無卡頓，並手動停止 90.92 秒片段。這提供本次選路假說的依據，**不是本版本修復成功的證據**。

共用 C／Python 幾何公式增加 `record_preview`，預設關閉。SensorLab 只依既有 `o->fast` 開啟：自訂引擎速率 >99 時，若 C 路徑來源 ≤2100×1710 且有效寬 ≤2000，優先從錄影影像取預覽。否則保持原有選路。B／D、CRCT bin 原規則保留；不使用尺寸／RECIPE 特例。

全部預覽尺寸仍交給既有 `isp_visible()`，沒有另一套比例計算。感光元件時序、實際錄影速率、錄影尺寸、DNG DefaultScale 與已驗收的顯示比例公式不改。無新 hook、配置、全幅 CPU 複製、USB 或儲存寫入。AP ABI 2、QS API 6 與持久化設定格式沿用；`core_spec` 的新增欄位只存在於一同編譯的內部計算結構。

代價：例如本案例預覽有效尺寸由約 672×196 改為錄影的 320×196，放大到 LCD 時可能較粗；這是選用低解析度錄影影像作預覽的結果。

## 驗證

`test_hirate_route.py` 在模擬器中實際執行 SensorLab 套用、原廠 canvas gather 與純原廠 CRCT selector C0325228–C03255B0。selector 沒有外部替身；輸入遵照 C031D988 的欄位抽取及預設值；不明指令位址立即失敗。模擬器內還原 selector 原字以單獨驗證路由，沒有改真實韌體；此批 3×6 沒有 CRCT bin 修正要套。

- 舊來源：11b／12b 3×6 ×144／200／209 fps 都為 `[0,0,1] / [1,3] / record1`；`baseline.json` 六個反例失敗、零測試錯誤。
- 新來源：上述六例為 `[0,1,0] / [1,4] / record0`，使用原錄影縮放，預覽有效 320×196；`candidate-final.json` 通過。
- 25／100／119.88 fps 仍是原預覽；高→低重新套用恢復；來源寬高超限、C 會增加視野裁切的案例保持 E3。
- `mutant-no-tap.json`：孤立副本移除新選路，六例失敗；`mutant-no-visible-bound.json`：移除完整視野限制，特定邊界失敗。兩者可編譯、零測試錯誤。
- `regression-final.log` 95 項、`qs-regression.log` 9 項、`settings-migration/report.json` 8 項，全數通過，共 112 項。
- `core-regression-final.log`：C／Python 1,479,189 個比較零差異，含預設選路、隨機 opt-in、非法值、邊界及 ARM 執行。
- default／repro 兩次建置逐位元組一致；ZIP、來源與壓縮證據均核對，見 `REPORT.json` 與外部 archive-check。

這是路由與資料一致性驗證，**未模擬持續錄影的 DMA、RTOS 排程、LCD 或儲存硬體；根因及實機改善仍未證實**。v0.7.10 回放修正保留且回歸通過，實機回放也未取得新驗收結果。

## 交付與下一步

關機後只更換 SensorLab BIN；QSContainer v0.3.4、AutoRun／LOADER 沿用。本包使用預設設定，需重選原本配置。
