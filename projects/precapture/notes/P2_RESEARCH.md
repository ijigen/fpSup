## 1. 结论（先看这里）

原计划是"S1 按住**且 AF 完成后**注入 S2 ON"，需要找一个"对焦完成"的钩子。
研究发现**原厂已经内建这个行为**，所以不需要对焦钩子：

- 在等对焦（WAIT_AF）或对焦锁定（HOLD）状态按下 S2 时，如果相机"还不能拍"
  （`FUN_c039ab38(mgr,0) == 0`，即对焦优先、尚未合焦），原厂**只把 S2 记成待处理**
  （按键状态字节 `[2] = 1`），不立刻拍。[F]
- 对焦完成后，状态机每帧的处理函数检查到"能拍了"且 `[2]` 待处理，就**自己开拍**
  （`FUN_c0397e60(…, 3, …)`，走 kind 9 → HIGHCONT）。[F]

所以 H1 可以简化成：**看到 S1 按下（码 4）就紧接着分发 S2 按下（码 6）**。
对焦优先时，连拍会等到合焦才开始——这正是"S1 且 AF 完成后开始"，由原厂自己保证。

**好处**：H1 与 H4 都放在**同一个**钩子位址（按键线程的分发调用点），只用原厂键码，
不碰对焦内部、不碰状态机结构。这比在对焦流程里找钩子安全得多。

**行为差异（需要使用者确认）**：`FUN_c039ab38` 是否"能拍"取决于对焦设定。
对焦优先（AF-S 常见）时会等合焦；**释放优先、AF-C、MF 时会立刻返回"能拍"，
连拍在按下 S1 的当下就开始，不等对焦**。对预录来说这多半可以接受（按时间挑帧只留最后 0.5 s），
但和"AF 完成后才开始"的字面要求不同。

## 2. 按键分发：唯一的钩子位址 [F]

- KeyMon 单例 `FUN_c02dbaf0()` = `0xC3425684`。
- 投递 `FUN_c02dbbe8(keymon, code)`：投到 `keymon+0x24` 的队列，超时 3000。
- 按键线程 `FUN_c02dc0a8`：循环取码 → 持锁（`FUN_c0010298(…, keymon+0x20)`）→
  **`C02DC108: bl FUN_c02dc138`**（r0 = keymon，r1 = 码）→ 放锁 → 码 0x75 时退出。
- **`FUN_c02dc138` 全映像只有这一个调用点**（`fwidx callers c02dc138` → 只有 `c02dc108`）。
- `FUN_c02dc138(keymon, code)`：依次把码交给 `keymon[0..6]` 七个监听者的 `vt+0xC`，
  返回 0 的监听者被清掉。同步执行，在按键线程里。
- 调用点之后只用 r5（码，callee-saved）比较 0x75 → 把这条 `bl` 换成 `bl 跳板`，
  包装函数遵守 AAPCS 即可，与 P1 换 `blx` 同一种做法。

## 3. 状态对象与按键状态 [F]

基类建构 `FUN_c03a9868(obj, id)`：

| 栏位 | 值 |
|---|---|
| `obj[0]` | `0xC351FF34`（按键状态字节数组：[1] = S1，[2] = S2） |
| `obj[1]` | `FUN_c0399c90()`（对焦／拍摄管理物件） |
| `obj[2]` | `FUN_c03a6398()` |
| `obj[3]` | 本状态 id |
| `obj[4]` | vptr |

`FUN_c03a92b0(base,i)` 读、`FUN_c03a92d0` 置 1、`FUN_c03a92f0` 清 0。

各状态 vtable（`fwidx vt` 口径，fn0 = vptr+8）的按键槽：

| 槽 | 意义 | THR | WAIT_AF | HOLD | HIGHCONT |
|---|---|---|---|---|---|
| +0x04 | S1 ON | C0393838 | C03942D0（置 [1]） | C038F8B8 | C038E700（置 [1]） |
| +0x08 | S1 OFF | C0393888 | C0394308（清 [2][1]） | C038F930 | C038E728（只清 [1]） |
| +0x0C | S2 ON | C03938B0 | C0394398 → C03954A0 | C038FA48 | C038E750（只置 [2]） |
| +0x10 | S2 OFF | C03939B0 | C03943C8（清 [2]） | C038FB70（清 [2]） | C038E778（清 [2]，收尾） |
| +0x8C | 每帧／对焦事件 | C0393FA8 | C0394928 | C03900E8 | C038EAF0 |

要点：
- **HIGHCONT 放开 S1 只清 [1]，连拍继续**；只有 S2 OFF 才收尾（`FUN_c038f720`）。
  → 放开 S1 时必须补一个 S2 OFF，否则连拍停不下来（只能等 10 s 超时）。
- WAIT_AF 的 S1 OFF 会同时清 [2]：对焦还没完成就放开 S1，待处理的 S2 会被丢掉，不会拍。

## 4. 拍摄类型判断 `FUN_c0397b30(key)` [F]

S2（key 3）时返回 9（高速连拍）的条件：非电影模式（`FUN_c0207088(FUN_c0206e98())+0xB8 != 1`），
录制设定 `+0x48 == 1`（连拍），`FUN_c03881e8()` 非 0（速度表项第 10 字节），
`+0x1D9 == 0`、`+0x193 == 0`、`FUN_c0208620() == 0`。

- 只读设定；内部单例 getter 有"首次使用才建构"的保护字，进入拍摄模式后都已建好。[I]
- `FUN_c03881e8 → FUN_c0388790` 在速度表里找不到当前档时会断言（`FUN_c0011100`）。
  原厂每次在连拍下按 S2 都走同一条路，所以档位一定在表里。[I]
- 用途：H1 只在 `FUN_c0397b30(3) == 9` 时注入——和原厂按 S2 时的判断完全相同，
  中速／低速连拍、单张、电影模式都不会被触发。

## 5. P2 设计（单一位址 + 沿用 P1 每帧位址做超时）

钩子 **H1/H4：`C02DC108`**（`bl FUN_c02dc138` → `bl 跳板`），在按键线程里：

```
dispatch(keymon, code):
  if code == 4 and not pre and kind_is_highcont():   # S1 ON
      orig(keymon, 4)
      pre = 1; t0 = now()
      orig(keymon, 6)          # 直接同步分发 S2 ON，不经队列（避免按键线程投给自己的队列）
      return
  if code == 5 and pre:                              # 只放开 S1
      pre = 0
      orig(keymon, 7)          # 先 S2 OFF（原厂 s2off→s1off 顺序）
      orig(keymon, 5)
      return
  if code == 7:                                      # 实体 S2 放开或超时注入的 S2 OFF
      pre = 0
  orig(keymon, code)
```

超时：沿用 P1 的每帧位址（B 点 `C038F174`、A 点 `C038F0E8`，原样放行）。每帧检查
`pre && now - t0 > 10 s && !timeout_sent` → `timeout_sent = 1`，用 `FUN_c02dbbe8(keymon, 7)`
投递 S2 OFF（跨线程投递，和 shell `key S2OFF` 相同）。按键线程分发这个 7 时清掉 `pre`。

为什么在按键线程里直接调用 `orig` 而不是投递：线程自己投给自己的队列，队列满时会卡 3 s；
直接调用和线程处理一个取出来的码完全一样。

### 5.1 实现中加的前置检查

`FUN_c0397b30` 用到的单例 getter 第一次被调用时会建构物件；`FUN_c0022e08` 在设定栈状态不对时会断言。
所以调用它之前先做只读检查，不过就不注入、原样放行，原因写进 `P_GATE`：

| P_GATE | 意义 |
|---|---|
| 0 | 还没有半按过 |
| 1 | 已注入（高速连拍） |
| `0x100 | kind` | 不是高速连拍（例如单张 0），不注入 |
| `0x200 | n` | 第 n 个单例还没建好：1 `FUN_c03a9970`(0xC35A9530)、2 `FUN_c0206e98`(0xC31F8C90)、3 `FUN_c0387e40`(0xC358CB48)、4 `FUN_c00213b8`(0xC3074980)、5 `FUN_c0022da8`(0xC3075684) |
| `0x300` | 设定栈 0xC3075670 状态不对（`[+0xC] != 1`、`[+0x10] >= 3` 或该格为 0） |

保护字与设定栈的地址来自反编译，若有误，结果是**永远不注入**（P_GATE 会显示原因），不是误注入。
