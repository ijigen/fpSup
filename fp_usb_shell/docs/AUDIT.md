# 用韌體知識回頭審視這個 shell

2026-08-27。讀了韌體自己怎麼讀檔、怎麼配記憶體之後,回來看這裡有多少東西是
「我們自己發明的」而韌體早就有正規做法,以及有多少純粹是多餘的。

## 已經拿掉的

| | 為什麼 |
|---|---|
| `DUMP_TEXT` | 定義了,沒有任何程式碼讀它。是 `dump.S` 印十六進位時代的暫存區偏移 |
| `_no_raw` fallback | 用來應付「不懂 raw 回覆的 worker」。已經沒有那種 worker 了 |
| `read_bulk` 寫的第三個參數 | `dumpraw` 從來不讀它。四個命令搬一塊,其中一個純浪費 |
| `put` 的 `read_back` 驗證 | 換成 `read_bulk`:22 KiB/s → 351。`put_slow` 保留舊做法,因為 dumpraw 是它放進去的 |
| `dump.S` | 標記為已被取代,留著當「為什麼不要用 printf」的實測紀錄 |

## 我們自己發明、而韌體有正規做法的

**記憶體配置。** 開機用 `memmgr bufmem get` 搶 1 MB,然後手動算偏移:陀螺儀在這、
擷取緩衝在那、檔案暫存區接在後面,還有一個主機端常數 `POOL_SIZE` 記著總量。沒有人檢查,
撞到了症狀會出現在無關的地方。

韌體有真正的配置器,而且相機自己的程式碼就在用(照片回放要 10 MB、韌體更新要 32 MB)。
`getfile` 已經改用它 —— 實測配得到 32 MB,是整個舊池的三十二倍。見 `heapalloc.S`。

**還沒改的:** `putfile` 的暫存區、AutoRun 開機那 1 MB。後者要先確認
**AutoRun 執行的時機堆積準備好了沒** —— 當初用 `memmgr bufmem get` 很可能就是因為太早。

**讀檔的問法。** 韌體從不問檔案多大,它配一塊夠寬的緩衝、要求量開好開滿、用回傳的實際長度。
CinemaDNG 回放甚至把「要求量 == 實際量」當成錯誤(表示被截斷)。`getfile` 已經照做,
連帶讓 poison 標記在那條路上變成多餘 —— 韌體回報的長度做同一件事,而且更可靠。

**快取一致性。** 韌體的檔案緩衝是可快取的,靠 `FUN_c000e91c()` 明確維護。我們現在靠
「逐位元組複製到擷取緩衝」把問題洗掉,那是誤打誤撞,不是設計。

## 還多餘、但要動 worker 才能拿掉

**`dumpraw` 的那次複製。** 它把資料逐位元組抄進擷取緩衝,worker 的 TRB 再從那裡 DMA 出去。
TRB 大可直接指向來源。要動的是 worker:它把回覆指標寫死成 `FRAMEBUF[0] + 0x2000`,
得多一個「擷取指標」字讓載荷覆寫。

拿掉之後同時消失的還有 **16 KiB 的塊上限** —— 那是擷取緩衝的大小,不是任何硬體限制
(單一 TRB 上限是 16 MB)。31 MB 的檔案現在要 2000 個來回,理論上可以是 2 個。

**worker 迴圈的窗口。** 迴圈是嚴格串列的:備妥 OUT → 等命令 → 執行 → 回覆 → 回到頂端 →
備妥 OUT。「回覆完」到「重新備妥」之間主機的下一個命令沒有地方落腳,而 `arm_out` 進門
第一件事是 `EndTransfer`,可能把已經落地還沒取走的命令丟掉。

2026-08-27 實測:300 個區塊請求,**worker 自己 fault 了 80 次**,另有約 8 個命令
根本沒到相機。主機只感覺到 6 次失手,因為重試把其餘的蓋掉了。**這不是雜訊,是我們
自己的設計缺陷**,而且一直被重試掩蓋著。

要修得先知道是四個呼叫中的哪一個失敗(`arm_out` / OUT `wait` / `arm_in` / IN `wait`),
worker 只保留最後一次的狀態,而最後一次總是成功的。鎖住第一次非零的狀態就會知道 ——
純記錄、不改行為,跟 gate 那個鎖存同一種改法。

## 順手記下的地雷

- **`dir` 的路徑**:根目錄要 `dir \\`(雙反斜線),**子目錄要單的**(`dir \DCIM\100SIGMA`)。
  指令自己印的用法範例是錯的。
- **比對韌體映像前**要先套用 `build_autorun.py` 的 `PATCHES`/`SCREEN` —— 映像不含我們的
  開機修補,4 MB 以上的讀取會撞到 `0xC03E4698`/`0xC03E46A0` 而看起來像損壞。
- **配置器要用四參數那組**(`FUN_c001d740`)。照片路徑的 `FUN_c001d038` 有五個參數,
  第五個依 AAPCS 走堆疊,`callfn` 只設暫存器,傳過去是垃圾。

## AutoRun 本身

586 行、**503 個命令**,其中:

| | |
|---|---|
| 400 | `mem set` 寫 worker 的程式碼 —— **一個字一個命令** |
| 90 | `display osd` / `display text` 的進度條與收尾 |
| 11 | 端點與螢幕修補 |
| 1 | `memmgr bufmem get 0 1048576` |
| 1 | 掛上 hook |

**八成的 AutoRun 是在把 1532 位元組一個字一個字搬進去。** 而那個進度條之所以存在,
就是因為這件事很慢 —— 註解自己寫了:「不加的話讀數會卡在 90% 幾百個無聲的命令,
看起來就像當掉」。

### 沒有 `mem load`

shell 有 `mem save`(記憶體 → 檔案),**沒有反向的**。所以用內建命令沒辦法把程式碼
從檔案載進來,只能一個字一個命令。

### 已經改好了 (2026-08-27,實機開機驗證通過)

寫一個小的載入器(約 200 位元組 = 50 個命令),讓它自己去讀 `\VSHL.BIN` 並啟動。
AutoRun 就變成:修補描述元 → 寫載入器 → 載入器讀檔 → 啟動。

**400 個命令變成 50 個,而且不隨程式碼變大而增加。** 現在加陀螺儀那 3360 位元組要多
840 個命令;改完之後是 0 個。進度條也可以跟著縮。

`templates/loader.S`(512 bytes),`build_autorun.py --loader`。實測:

| | 原本 | 現在 |
|---|---|---|
| AutoRun 命令數 | 503 | **248** |
| 寫程式碼的命令 | 400 | 128,**不再隨載荷增加** |

開機時檔案系統確實可用 —— 這點本來就有間接證據(AutoRun 自己就是從卡片讀出來的)。

**上線前後各踩到一個 bug,兩個都值得記住:**

1. **`putfile` 用 mode 7,不會截斷。** 新 AutoRun 比舊的短,卡上就變成「新腳本 + 舊腳本的
   尾巴」,而那尾巴是 400 個寫舊 worker 的 `mem set` —— 會在載入器掛好之後把它整個蓋掉。
   解法:**所有版本一律補到 32 KiB**,長度固定,短版永遠蓋得住長版。
2. **載入器不能住在它要寫入的位址上。** 第一版放在 `LOAD`(0xC072F050),而它複製的目標
   也是那裡 —— 複製迴圈執行到一半就把自己的指令換掉了。那次能跑完是指令快取撐住的,
   不是設計。現在放 `0xC072DE64`。
3. **重入保護不要借別人的狀態字。** 第一版借 worker 狀態區的 `+0x3C`,而 worker
   **每次成功回覆都會清掉它** —— 旗標在 worker 啟動後一毫秒內就沒了。現在載入器自己帶。

### 那 1 MB 的池

保留 1 MB 是為了「暫存四分之一 MB 的檔案」。現在 `getfile` 的緩衝改跟韌體要了,
`putfile` 的暫存區也可以 —— 之後池裡真正需要的只剩:

```
+0x0000  frame buffer   4 KiB
+0x2000  capture buffer 16 KiB
+0x6000  載入物的自用緩衝
```

也就是 **64 KiB 就夠,不是 1 MB**,可以還將近一 MB 給相機。

⚠️ 但 `memmgr bufmem get` **只能傳三個參數**(第四個會被解析成 size),而且
**基底位址會隨要求的大小而變** —— 註解記著:從 4 KiB 改成 64 KiB 就讓基底從
`0x44F6ADC0` 移到 `0x45026680`。所有位址都是從那個指標推出來的,所以改大小是安全的,
但一定要重測。

### 收尾的三次重複

`display osd 1` 和 `display text` 各重複三次,不是多餘 —— OSD 圖層跑三個緩衝,
少一次就會透出舊畫面。這條要留著。

## request 與 reply 共用緩衝 (2026-08-27,改了又退回)

`arm_out` 把 OUT 的 TRB 指向 `FRAMEBUF[0]`,而 `serve` 把回覆的表頭也建在同一個地方 ——
**response 寫在 request 的框架上**。兩個後果:

1. 今天稍早那個「回覆超過 44 位元組就壞、`version` 回不來」的 bug,原因是 `reply` 在迴圈
   頂端讀收到的 flags,而 `fill_header` 每幀覆寫同一欄位。當時只把讀取移出迴圈,治了症狀。
2. **回覆還在用那塊緩衝,就不能提前備妥接收** —— 所以 `arm_out` 只能排在回覆之後,
   也就是控制器剛結束一筆 IN 傳輸的那一刻,而它在那裡有 12–52% 被拒絕。

**改了:** request 落在 `+0x000`、副本 `+0x800`、回覆框架 `+0xA00`,`arm_out` 移到收到請求
之後、回覆之前。

**結果違反直覺,所以退回了:**

| | 分家前 | 分家後 |
|---|---|---|
| 相機端 fault | 80 / 300 輪 | **0** |
| 4 MB 讀取 | 0.35 s | 10–38 s |
| 主機收不到回覆 | 少見 | **32% 的塊**(245 塊裡 78 塊逾時) |

`arm_out` 的失敗確實**完全消失**,但回覆在回程大量遺失,而相機自己認為每輪都送出了
(`faults = 0`)。原因未知。分家版留在 `worker.S.split`。

**過程中自己造成的三個 bug,都值得記住:**

- **改了一半比不改更糟。** 把「回覆建在哪裡」改了,忘了改 `arm_in`「從哪裡送」——
  相機把 request 原樣送回,`version` 回答 `"shl version"`。
- **失敗的那一輪什麼都沒備妥,而下一輪不會補** —— 開機第一次 arm 失敗後就永遠聾著,
  賠一趟讀卡機。修法:每輪開頭視需要備妥。
- **`import build_autorun` 會重建 AutoRun** —— 那是腳本,import 就執行。兩支測試腳本
  為了拿 `PATCHES` 而 import 它,默默把載入器版蓋成單檔版。修補清單已拆到 `patches.py`。
