  lookup 的 table pointer。非 OG3K 的 FHD/UHD key 交回原廠 lookup 時,
  r1 可能已成為 0/3/4,違反原廠函式的暫存器契約。

★ 本版新增:8-bit / 10-bit CinemaDNG(2026-09-15)
  v0.2.1a 的缺陷:選 8-bit 或 10-bit 品質時,OG3K **會錄成 UHD30**。
  picker 有三張表,選表的 *(param_2+0x20) 就是 eRawBitType
  (4 = 8-bit → 0xC0BE5810、3 = 10-bit → 0xC0BE59B0、其餘 = 12-bit → 0xC0BE5B50),
  三張都是 CinemaDNG。v0.2.1a 只註冊在 12-bit 那張,另外兩張查不到鍵,
  原廠的錯誤退回給出 &DAT_c0be5b50 = 表3 第 0 筆 = UHD30 / p171 / mode 7 ——
  連使用者選的位元深度都一起丟掉。

  修法只動兩個既有 payload,沒有新掛 hook,沒有改任何原廠資料:
    fmttable.S    比對三張 picker table,命中 OG3K 時把 eRawBitType
                  鎖存到 0xC0731C14(只在命中時寫,不會被別的查詢污染)。
    og3kcanvas.S  錄影 case 依鎖存值寫畫布 RAM 複本的平面格式碼:
                      8-bit  +0x080 = 10  +0x084 = 10
                     10-bit  +0x080 = 10  +0x084 =  9
                     12-bit  +0x080 =  7  +0x084 =  7
                  (bpp 對照 FUN_c04356b0:7 → 12-bit、9 → 10-bit、10 → 8-bit。
                   這兩欄就是原廠 p131/p151/p171 三胞胎 65 欄裡唯一不同的兩欄。)

  DNG 的 BitsPerSample 由 FUN_c06a5290 用 FUN_c02da870(eRawBitType) 算,
  不看 profile;把 +0x084 對齊 eRawBitType,標籤與資料就自動一致。

  實機驗證(2026-09-15,rec log-out 的 file-size,每幀位元組數):

  中央區 G/R = 0.951 / 0.962 / 0.962,無綠偏,3:2 滿幅,29.97p。

借用的 profile 是 **p83**(S 尺寸 12-bit 照片的拍攝 profile)。
  它的 PARAM 列與 p43 只差 +0x030,而張數原廠就是 3,所以不需要
  寫畫格率。**所有幾何都只改畫布的 RAM 複本,原廠 PARAM 列一個位元都不動。**
  早先借 p43 要寫畫格率,那會讓 S 尺寸照片檢視多要三張 RAW 緩衝 ——
  拍一張 S 尺寸照片就會凍結。改用 p83 之後已驗證消失。

原生 ISO / 高光餘裕(12-bit):**已修正**(2026-09-14)。
  OG3K 的擷取原本拿到 gain_state 3(雙原生 HCG 門檻 ISO 640),
  在 ISO 640 以上就切到高轉換增益 —— 比原廠 12-bit CinemaDNG
  (gain_state 7,門檻 3200)**少約 2.7 檔高光餘裕**,而且因為機內回放
  固定補 +3 EV,回放會過曝 2.7 檔。
  實測:修正前 raw 比原廠 FHD 亮 2.675 EV、BaselineExposure +0.322;
  修正後兩者完全一致(+3.000,同場景中位−黑階 3.0 vs 3.0)。
  修法 og3kgs.S:只 hook 增益分派的判斷 FUN_c03a6dd8,不動感測器模式。
  同時把預覽平面格式 +0x080 補成 12-bit(原廠影片是 7,照片 profile 是 10),
  否則錄影預覽會偏綠並閃爍。本版把這一筆改成依位元深度三選一。
