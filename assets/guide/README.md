## Use video, not GIF

A ten-second screen recording is often 5–20 MB as a GIF and a few hundred KB as
MP4. Autoplaying muted video looks exactly the same to the viewer:

```html
<video src="assets/guide/06-boot.mp4" autoplay loop muted playsinline></video>
```

All four attributes matter. `muted` is what allows autoplay at all, and
`playsinline` stops iOS taking the video fullscreen. A still image is:

```html
<img src="assets/guide/01-firmware.jpg" alt="what it shows">
```

Keep the `<figcaption>` line that is already there either way.

## Sizes

The page is 860 px wide at most and images are shown at full width, so
**1720 px wide covers a 2× screen**. Anything larger is only download time.
Photographs as JPEG around quality 80; screenshots of menus and text as PNG.
Video: H.264 MP4, no audio track at all.

Nothing here is generated by a script — unlike the rest of `assets/`, which
`tools/build_assets.py` writes. Do not run that expecting it to touch these.


## Where the step 1 pair came from

Pulled off the camera over the USB shell rather than photographed:

```sh
cd fp_usb_shell
./host/fpsh 'dir \DCIM\100SIGMA'                 # SS__ files are the camera's own screenshots
python3 getfile.py '\DCIM\100SIGMA\SS__0590.JPG' out.JPG --size 153359
```

**The serial number in `01-firmware-info.webp` is pixelated.** The camera prints
it on that screen next to the version, and the original frame had it in full.
Anything else taken from this screen needs the same treatment before it is
published.


## Encoding the walkthroughs

The two step 7 clips came in as 3028x1898 60 fps screen recordings, 29 MB for
the pair. What ships is 1280 wide, 30 fps, no audio:

```sh
ffmpeg -i in.mov -vf "scale=1280:-2,fps=30" \
       -c:v libx264 -crf 30 -preset slow -pix_fmt yuv420p -an \
       -movflags +faststart out.mp4
ffmpeg -ss 40 -i out.mp4 -frames:v 1 poster.png     # then WebP at q80
```

3.7 MB for the pair, and the UI text stays readable -- crf 26/30/34 were compared
on a frame of the Gyroflow sidebar and all three were legible, so 30 is the
middle one, not a guess.

**These carry `controls`, `preload="metadata"` and a poster, not `autoplay loop`.**
They are 98 and 49 seconds -- walkthroughs, not the GIF-substitute loop a
ten-second clip wants. Measured on the built page: the two posters are 88 KB and
`readyState` stays 0, so not one byte of MP4 is fetched until somebody presses
play.

`avconvert`, the transcoder built into macOS, is not a fallback here: given these
sources it produced 87 MB and 52 MB files, larger than the originals.
