The 70 sensor modes

Every way the fp knows how to read its sensor, as a table in ROM. This is all 70 of them, every field in the record explained, and a searchable comparison — including the fields nobody has worked out.

  • 70 modes
  • 13 rasters
  • 17 frame rates
Where it is
Three separate tables describe a mode. The one below is the metadata table at 0xC0B59DC0: 70 records of 0x64 bytes, 25 words each. Everything on this page is read straight out of it.
On “70 parameters”
70 is the number of modes, not of parameters. Each mode's metadata record has 25 fields; the separate register record has 162, of which 133 vary between modes. The 70 is what gets picked from, not what is in each one.
What is not solved
Four of the 25 metadata fields are always zero, two are read from a single mode's investigation rather than proven across the table, and the 162-field register record is almost entirely unmapped.

Three tables, one mode

Every field in the metadata record

25 words. Confidence is marked per field: read means the meaning is visible in the data or in code, inferred means it comes from one mode's investigation and has not been checked across the table, and unknown is unknown.

+0x00mode idread The key every other table uses. Not an index — ids run 0 to 221 with gaps, and the table is not sorted by them. 70 distinct · 0 … 221
+0x04 / +0x08raster width / heightread What the sensor actually reads out. This is the number that decides bandwidth and, with the timing table, rolling shutter. 8 widths · 13 distinct rasters · 2016×672 … 6064×4042
+0x0C / +0x10—unknown Zero in all 70 records. Position suggests an origin for the pair above, but nothing ever sets it, so that is a guess from layout alone. always 0
+0x14 / +0x18second width / heightread Identical to +0x04/+0x08 in all 70 records. Why the record carries the same geometry twice is not known. identical to +0x04/+0x08, 70/70
+0x1C / +0x20—unknown Zero in all 70 records, same shape as +0x0C/+0x10. always 0
+0x24 / +0x28third width / heightread Identical to the other two in 69 of 70 records. The exception is mode 100, where the first two say 4176×2174 and this one says 3032×2174 — same height, different width. Whether that is meaningful or a typo in the firmware is not known, and nothing else in the table looks like it. differs only for mode 100
+0x2C / +0x30output crop width / heightread The active area inside the raster. Set on only 6 of 70 modes; the other 64 leave it zero, meaning the whole raster is the output. 0 (×64) · 3000×2000 (×2) · 6000×4000 (×4)
+0x34 / +0x38crop origin x / yread Top-left of that crop. Only set on the same modes as the pair above. 0 · (16, 6) · (32, 21)
+0x3C14-bit flagread 1 on exactly 8 modes, 0 on the rest. Those 8 are the stills-class readouts — mode 0 is independently documented as RAW14, which is what fixes the polarity. 1 on modes 0, 6, 95, 100, 122, 129, 141, 144
+0x40nominal frame rateread Nominal, not exact, and it goes stale. Mode 3 says 30 and runs 29.97; mode 98 says 78 and runs 77.27; mode 121 says 25 and runs 24.9997. It also becomes an outright lie when a project retimes a donor mode — OG3K drives mode 98 at 29.97 while this field still reads 78. 17 values · 18 … 240
+0x44 … +0x50merge tuple (four factors)read Four reduction factors. Only four combinations occur across the whole table. The last two are confirmed as effective X/Y geometry scale — but that proves a coordinate ratio and says nothing about whether charge is combined or rows are skipped. The first two are not pinned down at all. (1,1,1,1) ×23 · (2,2,2,2) ×36 · (3,2,3,3) ×8 · (3,3,3,6) ×3
+0x54aspect markerread 2 on every 3:2 raster, 1 on every 16:9 one. Checks out against the geometry in all 70 records. 1 (×43, 16:9) · 2 (×27, 3:2)
+0x58full or cropped readoutread 0 for a full-width readout, 1 for a cropped one. Independent of the crop fields above, which describe an output window rather than the readout itself. 0 (×39) · 1 (×31)
+0x5Cvertical blankinginferred Named from the HSW investigation of a single mode. The value range is plausible for vblank lines and it correlates loosely with frame rate, but it has not been checked against the timing table across the other 69 modes. 14 · 30 · 40 · 50 (×11) · 70 (×44) · 100 (×10)
+0x60analogue fingerprint / readout classinferred Groups modes that share an analogue signature — the HSW work reads 23 as the “fast 330” MONIT class. Eight values across the table, and modes with the same value do tend to share a raster family, which is consistent. Not proven. 16 … 23, eight groups

The register record — 162 fields, mostly dark

The second table is what actually gets written to the sensor. A header at 0xC0B5FDA4 holds {pointer, 70}, and the records start at 0xC0B5FDAC with a stride of 0x288 — confirmed because the first word of each record reproduces the metadata table's mode-id order exactly.

of 162 fieldscountwhat that means
always zero13Reserved, or a feature this sensor does not use.
constant across all modes16Set once for the part, not per mode.
varying133The actual per-mode configuration. Almost none of it is identified.

Most of the varying fields take only two or three distinct values across all 70 modes, which is the signature of a mode class selector rather than a tuned number — the same value repeats for every mode in a raster family. A handful have wider ranges and look more like real timing or gain values.

This is the largest unexplored thing in the sensor path. 133 per-mode parameters, and the project has names for none of them. Everything the open-gate work does at the sensor level — retiming a donor mode — is done through the timing values, not through these. What they control is simply not known.

Timing — partially mapped

Frame rate and rolling shutter come from hmax, vmax and a tail value, not from the metadata field. For mode 12 the record near 0xC0B59A40 decodes cleanly:

+0x00   12              mode id
+0x04   330, 330        hmax, tail
+0x08   910, 6          vmax, ?
+0x24   911, 911        ?

frame period   330 x 909 + 330 = 300,300 cycles @ 72 MHz
actual rate    239.760240 fps          exactly, 0 ppm
rolling        330 x 672 / 72 MHz  =   3.080 ms
The table's extent could not be established. Walking outward from the mode-12 record by the stride that makes its first words look like mode ids (0x40) runs straight into the metadata table rather than stopping, and the ids it produces do not cover all 70 modes. Either the stride is wrong, the table is shorter than 70 entries, or it is indexed some other way. Only the mode-12 record is trustworthy here, and it is trustworthy because the HSW work derived 239.760240 fps from it independently.

What is still open

  • The 133 varying fields of the register record — the biggest gap on this page by a wide margin.
  • The timing table's stride, extent and indexing. Without it, rolling shutter and exact frame rate can only be quoted for modes somebody has already investigated.
  • Why the metadata record carries its geometry three times, and why mode 100 is the one record where the third copy disagrees.
  • What +0x0C/+0x10 and +0x1C/+0x20 are for. They are zero in every record, so nothing can be inferred from the data alone.
  • Whether the merge tuple means charge binning or row skipping. The last two factors are confirmed as geometry scale, which does not settle it, and the noise analysis that tried to settle it hit a modelling contradiction.
  • +0x5C and +0x60 are named from one mode's investigation and have not been verified across the table.

Sources

The field names for +0x5C and +0x60, and the mode-12 timing decode, come from the HSW investigation; the RAW14 identification that fixes the polarity of +0x3C comes from the sensor-mode work.
