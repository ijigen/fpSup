The 70 sensor modes70 個感光元件模式

Every way the fp knows how to read its sensor, as a table in ROM. This is all 70 of them, every field in the record explained, and a searchable comparison — including the fields nobody has worked out.

fp 知道的所有「讀取感光元件的方式」,全部存在 ROM 的一張表裡。這頁是全部 70 種,每個欄位逐一解釋,加上一張可以搜尋排序的對照表 —— 包括那些到現在還沒人搞懂的欄位。

  • 70 modes種模式
  • 13 rasters種光柵
  • 17 frame rates種格率
Where it is表在哪
Three separate tables describe a mode. The one below is the metadata table at 0xC0B59DC0: 70 records of 0x64 bytes, 25 words each. Everything on this page is read straight out of it.
一個模式是由三張分開的表描述的。下面講的這張是 metadata 表,在 0xC0B59DC0:70 筆,每筆 0x64 bytes、 25 個字。這頁的每個數字都是直接從它讀出來的。
On “70 parameters”關於「70 個參數」
70 is the number of modes, not of parameters. Each mode's metadata record has 25 fields; the separate register record has 162, of which 133 vary between modes. The 70 is what gets picked from, not what is in each one.
70 是模式的數量,不是參數的數量。 每個模式的 metadata 記錄有 25 個欄位;另一張 register record 有 162 個, 其中 133 個會隨模式改變。70 是「可以挑的東西有幾個」,不是「每個裡面有幾項」。
What is not solved還沒解的
Four of the 25 metadata fields are always zero, two are read from a single mode's investigation rather than proven across the table, and the 162-field register record is almost entirely unmapped. Timing is solved, so rolling shutter and exact frame rate are computed for all 70.
25 個 metadata 欄位裡有四個永遠是 0;兩個的名字是從單一模式的調查來的,沒有在整張表上驗證過;而 162 個欄位的 register record 幾乎完全沒被解開。時序表已經解開了,所以 70 個模式的捲簾和精確格率都算得出來。

The register record — 162 fields, mostly darkregister record — 162 個欄位,幾乎全黑

The second table is what actually gets written to the sensor. A header at 0xC0B5FDA4 holds {pointer, 70}, and the records start at 0xC0B5FDAC with a stride of 0x288 — confirmed because the first word of each record reproduces the metadata table's mode-id order exactly.

第二張表才是真正寫進感光元件的東西。0xC0B5FDA4 是個 {指標, 70} 的標頭,記錄從 0xC0B5FDAC 開始, stride 是 0x288 —— 這個 stride 能確認,是因為每筆的第一個字 完全重現了 metadata 表的 mode id 順序。

Most of the varying fields take only two or three distinct values across all 70 modes, which is the signature of a mode class selector rather than a tuned number — the same value repeats for every mode in a raster family. A handful have wider ranges and look more like real timing or gain values.

大部分會變的欄位,在 70 個模式裡只有兩三種值 —— 那是「模式類別選擇器」的特徵,不是調校過的數值:同一個光柵家族的模式共用同一個值。 少數幾個值域比較寬,那些看起來才像真的時序或增益。

This is the largest unexplored thing in the sensor path. 133 per-mode parameters, and the project has names for none of them. Everything the open-gate work does at the sensor level — retiming a donor mode — is done through the timing values, not through these. What they control is simply not known.
這是感光元件路徑上最大的未探索區。 133 個逐模式參數,而這個專案一個名字都給不出來。 open gate 在感光元件層做的所有事 —— 改借來的模式的時序 —— 走的是時序那些值, 不是這些。它們控制什麼,就是不知道。

Timing — solved時序 — 解開了

Frame rate and rolling shutter come from hmax, vmax and a tail value, not from the metadata field. The timing table is the descriptor's first pointer: 0xC0B59500, 70 records of 0x20 bytes, indexed by the same row number as metadata — all 70 rows carry a matching mode id.

格率和捲簾時間來自 hmax、vmax 跟一個 tail 值, 不是來自 metadata 那個欄位。時序表是描述子的第一個指標: 0xC0B59500,70 筆,每筆 0x20 bytes, 用跟 metadata 相同的列號索引 —— 70 筆的 mode id 全部對得上。

+0x04   hmax, tail          two u16
+0x08   vmax, ?             two u16

What went wrong the first time. This table was written up as unsolvable a day earlier. The stride was taken as 0x40 — exactly two records — which made a walk outward skip every other entry, produce an id list that covered only half the modes, and run past the end into the metadata table. The descriptor settles it without guessing: its first two {pointer, count} pairs are {0xC0B59500, 70} and {0xC0B59DC0, 70}, and the gap between them is exactly 70 × 0x20.
前一天為什麼弄錯。這張表在一天前被寫成「解不開」。 當時把 stride 當成 0x40 —— 剛好是兩筆的長度 —— 於是往外走時每次都跳過一筆,湊出來的 id 只涵蓋一半的模式,而且還會走過頭撞進 metadata 表。
描述子不用猜就能定案:它前兩個 {指標, 筆數} 是 {0xC0B59500, 70} 和 {0xC0B59DC0, 70}, 而兩者的間距剛好是 70 × 0x20。

What is still open還沒解的部分

  • The 133 varying fields of the register record — the biggest gap on this page by a wide margin.
  • register record 那 133 個會變的欄位 —— 這頁裡差距最大的一塊空白。
  • The unnamed half of the timing record's second word, and the five words after it. Frame rate and rolling shutter do not need them, so they were never chased.
  • 時序記錄第二個字裡沒命名的那半邊,以及它後面那五個字。算格率和捲簾用不到它們,所以一直沒去追。
  • Why the metadata record carries its geometry three times, and why mode 100 is the one record where the third copy disagrees.
  • metadata 記錄為什麼要把幾何存三次,以及為什麼 mode 100 是唯一第三份不一致的那一筆。
  • What +0x0C/+0x10 and +0x1C/+0x20 are for. They are zero in every record, so nothing can be inferred from the data alone.
  • +0x0C/+0x10 和 +0x1C/+0x20 是做什麼的。它們在每一筆裡都是 0,所以光看資料推不出任何東西。
  • Whether the merge tuple means charge binning or row skipping. The last two factors are confirmed as geometry scale, which does not settle it, and the noise analysis that tried to settle it hit a modelling contradiction.
  • 合併倍率到底是電荷合併還是跳列。後兩個因子確認是幾何倍率,但那不足以定案;想定案的雜訊分析撞到了一個模型上的矛盾。
  • +0x5C and +0x60 are named from one mode's investigation and have not been verified across the table.
  • +0x5C 跟 +0x60 的名字來自單一模式的調查,沒有在整張表上驗證過。

Sources出處

Every number on this page is read directly out of the Ver.5.02 image at the addresses given. The field names for +0x5C and +0x60, and the mode-12 timing decode, come from the HSW investigation; the RAW14 identification that fixes the polarity of +0x3C comes from the sensor-mode work. Where this page says a field is unknown, that is the current state and not a summary of someone else's conclusion.
