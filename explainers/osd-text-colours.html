On-screen text colours

The fp's display text colour is not a colour value. It is a palette index, one byte wide, and the other three bytes of the word are ignored. Here is what all 256 indices actually are.

  • 0–29 exact, from ROM
  • 30–160 empty
  • 161–255 measured on a camera
0xC0BB1208
Ink — the glyph strokes. Low byte = palette index.
0xC0BB120C
Background — the rest of the glyph cell. Same encoding; ships as 0, which is transparent.

Why it is an index

The OSD sub-layer is 8 bits per pixel through a colour lookup table. The glyph blitter (FUN_c052b620) writes one byte per pixel — the low byte of the colour word for a stroke pixel, the low byte of the background word for the rest. Whatever you put in the upper three bytes never reaches the screen.

That is why the stock value looks arbitrary. display text ships with 0xFFFFF8B2, whose low byte is 0xB2 — index 178. The firmware's own palette is thirty entries long. 178 is not in it.

The firmware palette — 0 to 29

Everything above 29

30–160 are empty — nothing has ever written them, and text drawn in one of those indices is invisible. 161–255 are not. The hardware CLUT is 256 entries (0x20D00000 + idx*4, packed U<<24 | V<<16 | Y<<8 | A), and the block above 160 is populated by the camera's own GUI, not by the thirty-entry table.

These are measured, and they are not ours. The CLUT window is write-only from the shell — it reads back zero in every plane access mode — so the only way to see what is in it is to draw each index and photograph the screen. The hex below comes from screenshots against a black backdrop, so it runs slightly dark and desaturated compared to the real entry. And nothing here belongs to the thirty-entry table: the camera's GUI can reload this block at any time. For anything that has to stay put, use 1, 3, 4, 5 or 7.

The stock pink lives here. Index 178, measured off the shipped display text output rather than off a swatch, is #FF6568. It is not a chosen colour — it is an out-of-range index that happens to land on a slot somebody else filled in.

How it was measured

Each index was drawn as text and photographed with the camera's own screenshot key, eighteen rows to a frame — the text's Y position is an immediate in the display text handler (MOV r8,#imm at 0xC03E4698), and mem set can rewrite firmware code in place, effective immediately, with no cache maintenance needed. Thirteen frames covered all 256.

One trap, paid for twice. mem set drops writes silently, so the Y immediate has to be read back and retried. The first pass did not, and the rows whose write went missing measured the live scene instead. The tell was that those "colours" tracked row position rather than index — every eighteenth index repeated the same value. That periodicity is also what identified 30–160 as empty.

While you are in here

There is one font and one size: 16×32 cells, 96 glyphs, 1 bpp, with 0 meaning ink and 1 meaning background. The second font object shares the same descriptor, so it is not a second size. The descriptor is in RAM at 0xC37830E8 — glyph width at +2, height at +4, bytes per row at +6, bitmap pointer at +0xC — so a larger font is a matter of uploading a scaled bitmap and repointing it. A 2× version is 24 KB and lands in under a second. The draw rectangle has to grow with it: DrawTextSimpleFont::v1 opens with if (rect.h < glyphHeight) return 0, so a taller font with the stock 32-pixel rectangle draws nothing at all.
