# 改選單:我們自己查出來的東西

SIGMA fp Ver.5.02。全部 RAM,拔電池就回原狀。

這份把散在 `notes/CANVAS_IS_NOT_THE_SETTINGS_BLOCK.md`、`notes/SHELL_COMMANDS.md`、
`notes/FRAME_RATE_IS_VMAX.md` 和 `projects/open-gate.md` 裡的選單相關發現收在一起。
**只收我們自己驗過的**,標註哪些實測、哪些推論、哪些沒測。

---

## 一句話

**任何選單項的值域與對應表,都在它自己的中繼資料裡,而中繼資料就在它名字字串的後面。**
不必追屬性框架,不必找觀察者。

---

## 1. 從 shell 能做什麼

```
menu                    根指令,底下 285 個 Set*
menu dump               印出 UI 設定區的十六進位傾印
menu <SetterName>       不帶參數 = getter,讀目前值
menu <SetterName> <n>   帶參數 = setter
```

**UI 設定區在 `0xC31B32BC`,2496 bytes。**(實測)

`menu dump` 最有用的用法是**前後比對**:切一次設定、傾印兩次、逐位元組 diff,
變動的那一個位元組就是它。動態解析度是這樣找到的 ——
**`0xC31B3A4C` 單一位元組**,`2` = FHD、`3` = UHD。

⚠️ **直接寫那個位元組不會傳播。** 值會變,但沒有任何下游知道。要有選單動作才會跑轉換。
這條害我們繞過一圈:以為找到了開關,其實只找到了被寫的地方。

### 指令表

`0xC0BBB5E8` 起,每筆三個字 `{名稱, 說明, 處理函式}`:

```
SetMovCinemaDNGQuality  -> 0xC03FD9D0
SetMovQuality           -> 0xC03FDA40
SetMovRecSize           -> 0xC03FDAB0
SetMovFramerate         -> 0xC03FDB20
SetMovBiningSupport     -> 0xC03FDB90
```

`FUN_c03fdab0` 的形狀,其他 setter 也一樣:

```c
有參數 → FUN_c005c020(FUN_c0057ae8(), 值, 1)
無參數 → FUN_c005c058()                        ← 所以不帶參數就是 getter
```

## 2. ★ 中繼資料註冊表 —— 這是最有用的一條

**`0xC0700000..0xC0760000` 是 `MenuItem*` 中繼資料的註冊表,263 個項目。**
每一個都是 `"MenuItemXxx\0"` 字串,後面緊接著它的參數。(實測,全掃過)

要查任何一個選單項:**找字串,讀它後面。** 就這樣。

`MenuItemMovieRecSize` 的完整樣子:

```
0xC0742204   "MenuItemMovieRecSize"
0xC0742218   0
0xC074221C   0xC0741DB8
0xC0742220   0
0xC0742224   22                    ← 型別標記
0xC0742228   2                     ← 列舉值
0xC074222C   1920                  ←   對應寬
0xC0742230   1080                  ←   對應高
0xC0742234   3                     ← 列舉值
0xC0742238   3840                  ←   對應寬
0xC074223C   2160                  ←   對應高
0xC0742240   "Invalid MovSize"     ← 錯誤字串
```

**只有列舉 2 與 3 合法。**

這順便訂正了一個我們自己的誤讀:先前掃 `SetMovRecSize` 0–13,記成「從 FHD 出發只有 3
會跳到 UHD,進了 UHD 之後其他值保持 UHD」,還據此推論「有隱藏尺寸但被擋住」。
**真相更簡單:其餘所有值都落到 "Invalid MovSize",什麼都沒做。**
一個看起來像「狀態相依行為」的東西,其實只是「無效輸入被忽略」。

### 全映像只有三個項目帶尺寸

```
0xC0742204  MenuItemMovieRecSize      [1920, 1080, 3840, 2160]
0xC0742860  MenuItemStillImageSize    [3840, 2160, 1920, 1080]
0xC074407C  MenuItemHdmiOutputFormat  [4096, 2160, 3840, 2160, 1920, 1080]
```

`MenuItemStillImageSize` 的佈局不一樣 —— **尺寸成對但沒有交錯的列舉值**,所以是位置索引
而不是 `{enum, w, h}`:

```
0xC0742880   22       與 MovieRecSize 相同的型別標記
0xC0742884   3840
0xC0742888   2160
0xC074288C   1920
0xC0742890   1080
```

它可疑的理由:`setting get cam_still_imagesize.h/v` 讀到 **1920/1080**。
fp 的靜態照片是 6000×4000,不該是這個數字 —— **除非 CINE 模式下「靜態尺寸」就是影片畫格尺寸**。
**已改成 3032/2012,未測。**

## 3. 改它有效,而且撐得過 record-start

```
0xC074222C  1920 → 3032
0xC0742230  1080 → 2012
menu SetMovRecSize 2
    → 主設定 0xC3074BE8 = 3032 x 2012
```

**然後錄一段,主設定還是 3032×2012 —— 沒有被刷回去。**(實測)

這是跟先前所有嘗試的關鍵差異。直接寫主設定,record-start 一重算就變回 1920×1080;
改中繼資料之後,**重算讀的就是我們改過的表,算出來的就是我們要的值**。

所以「設定是輸出不是輸入」那個死結解開了:**設定確實是輸出,但產生它的函數在我們手上。**

⚠️ **但這不改變錄下來的 DNG 尺寸。** 主設定變成 3032×2012,DNG 照樣 1936×1090。
所以設定 block 被排除為畫布來源 —— 改選單能改設定,但設定不是畫布。
(畫布最後是 `0xC043A19C` 的 geometry record,見 `projects/open-gate.md`。)

## 4. 屬性鏈:怎麼從指令走到中繼資料

用得上,但**下次不必再走一遍** —— 註冊表(§2)是捷徑。留著是因為它解釋了註冊表為什麼長那樣。

```
FUN_c0057ae8()        → 0xC31AC530      (CINE/STILL 開關也是這個物件)
*(obj+0)              → 0xC31AC59C
*(that+4)             → 0xC07397D8      vtable
*(that+0x1A0)         → 0xC0084700      accessor thunk
```

thunk 全是「回傳 `r0 + 固定偏移`」:

```
0xC0084700:  mov ip,r0 ; add r1,ip,#0x680 ; mov r0,r1 ; bx lr   → +0x680
0xC00846E8: → +0x664    0xC0084710: → +0x69C
0xC0084740: → +0x6D0    0xC0084768: → +0x704
```

所以屬性物件 = `0xC31AC59C + 0x680` = **`0xC31ACC1C`**。
注意是 `*(obj+0) + 0x680`,不是 `obj + 0x680` —— thunk 收到的 `r0` 是 `*(obj+0)`。

```
0xC31ACC1C  +0x00  0x69          屬性 id
            +0x08  0xC31AC540    擁有者
            +0x0C  0xC07421BC    vtable
            +0x14  2             ★ 目前值,等於 menu SetMovRecSize 讀回的值
```

vtable `0xC07421BC` 全是 `0xC00A8xxx` 的**通用**屬性類別(`+0x2C` 寫值、`+0x30` 衍生值變了、
`+0x34` 通知),所以轉換不在 vtable 裡。**`+0x3C` 指向 `0xC0742204`** —— 中繼資料。

⚠️ **這條鏈要用一次探針走完。** 手動分次 `mem get` 會抓到輪替中的值,拼出來的指標是假的。

**通知那條路不必追**(`FUN_c00A8DE0 → FUN_c0091288 → FUN_c00912f8 → FUN_c0091050`,
觀察者清單掛在 `0xC31AC540`)。`open-gate` 文件一度把「找出 `+0x1A0` 的觀察者」列為下一步 ——
**那一步不需要。**

## 5. 方法:為什麼搜尋找不到,位置才找得到

值得記,因為兩種搜尋都失敗了:

- **`0xC3075230`(設定 block 指標)在映像裡沒有對齊的字面值,也沒有 MOVW/MOVT 對** ——
  它是用 `base + offset` 取的。搜指標沒用。
- **`MOVW #1920` 全映像只有 1 處、`#3840` 3 處、`#2160` 1 處,而且互不相鄰。**
  常數不是內嵌的,所以一定在表裡。
- **相鄰字對 `(1920,1080)` 有 48 處、`(3840,2160)` 有 32 處** —— 雜訊太多,無法判別。

真正指出答案的是**位置**:`0xC074222C` 就在剛走到的屬性 vtable 後面 0x70 bytes,
而 vtable 的 `+0x3C` 正好指著那一區。

> **先走到物件,再看它旁邊有什麼。** 不要從常數往回搜。

## 6. 記位址時要標類別

重開機之後位址穩不穩,取決於它是靜態還是堆積:

```
穩定(靜態/BSS)   所有 0xC0xxxxxx 的表、0xC343B588 感光元件物件、
                   0xC352028C / 0xC359BE6C 的統計
不穩(堆積/緩衝)   寫入器描述環 0xC34B9F28 → 重開機後變 0xC34BB028
```

`0xC07xxxxx` 的選單中繼資料全部屬於前者,可以寫死在 patch 裡。
