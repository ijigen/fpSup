# ============================================================================
# USB shell.
#
# The camera keeps its own PTP gadget exactly as the firmware builds it, so the
# firmware owns the descriptors, creates and enables the endpoints, and
# re-creates them after a record-mode reconfiguration.  A few words are changed
# so nothing competes for those pipes and so PTP's unused interrupt endpoint
# becomes a second bulk IN for streaming; the rest of this file is the worker.
#
#   EP 0x01 OUT  commands      EP 0x82 IN  replies      EP 0x83 IN  streaming
#
# The worker understands one command: `shl <line>`, which runs <line> in the
# firmware's own shell and returns what it printed.  `mem set` and `mem save`
# come along for free, so the worker needs no memory commands of its own.
#
# Boot with the USB cable UNPLUGGED, then attach it.  The gadget is built on
# attach, so the patches have to land first; and the patched words sit in code
# that has not run yet, so no stale instruction-cache line can shadow them.
#
# The screen reads fpSup[........]0 through fpSup[########]100 while this runs
# and fpSup! when it is done.  A bar that stops means the load stopped there.
# ============================================================================

# --- DMA pool; its address lands in 0xC3757A7C -------------------------------
# +0x0000 frame buffer 4 KiB   +0x2000 capture buffer 16 KiB
# +0x6000 free for whatever is loaded alongside   +0x10000 template scratch
# Reserve the whole span up front rather than writing past the allocation and
# hoping the tail is free. Everything derives its address from this pointer:
# asking for 64 KiB instead of 4 already moved the base from 0x44F6ADC0 to
# 0x45026680, and every hard-coded address went with it.
# Three arguments, never four. The handler parses the alignment and stores it
# into the size slot -- `str r3, [sp, #4]` at 0xC03FA580, where the size went
# at 0xC03FA558; the alignment slot at [sp, #0xc] is only ever written with 0.
# So `get 0 0x20000 0x40` asked for 64 bytes and was handed the 128-byte
# minimum, while everything past it belonged to a 256 KiB buffer owned by
# 0xC03A4EEC that is reinitialised when recording starts. That is where the
# shell's capture buffer and anything loaded beside it had been living, and why
# the picture tore and the camera froze at unpredictable moments.
# 1 MiB. The USER pool reports 18 MB free in MOVIE_REC_DNG, and 128 KiB was
# not enough to stage a quarter-megabyte file -- which showed up as a verify
# that never converged rather than as an error, because the overflow landed in
# memory somebody else kept rewriting.
memmgr bufmem get 0 1048576
