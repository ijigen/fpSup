# 邊錄邊寫 gcsv — 設計(2026-08-27,未實作)

## 結論:不做(2026-08-27,有數字)

三次凍結、四次錄影之後,這條路**量出來比原本的方案差**,決定不做。留下的是量到的東西,
免得有人(我)再試一次。

| | 掉包 | 停止時卡片操作 | 錄影長度上限 |
|---|---|---|---|
| **停止時做(原本,現行)** | **0** | ~72 次 | 無 |
| 邊錄邊寫(每 60 KB 落盤) | **8811,約 26%** | ~2 次 | 無 |
| 累積到停止才寫 | 0 | ~5 次 | **約 20 秒** |

中間那欄不能接受,右邊那欄的長度限制在實用上也不能接受。

### 三次凍結的真正原因

不是開檔時機、不是寫入執行緒握鎖、不是配置器的呼叫 context ——
**是握著韌體配置器給的記憶體跨過錄影開始**。對照實驗:握著 64 KiB 錄影 → 凍結;
不握著 → 正常,池頂端的標記 16/16 存活。兩次都**沒有載入任何我們的程式碼**。
記在 `allocator-not-across-recording`。

把緩衝改成池頂端之後,邊錄邊寫**不再凍結**,檔案也正常產生 —— 露出來的才是真正的成本。

### 掉包是卡片寫入,不是轉文字

把 flush 改成只倒掉不寫卡(轉換照做):**`dropped` 從 8811 變成 0**,停止路徑 0.022 秒。
所以把 1900 筆樣本轉成文字便宜到量不出來,貴的是每 60 KB 多寫一次卡。

機制:環形緩衝由**陀螺回呼**抽進 A/B 兩個區塊緩衝;寫入執行緒慢下來 → 兩個都滿 →
回呼沒地方放 → 掉包。區塊約 766 ms 填滿一個,而**單次 SD 寫入最壞 692 ms** ——
多一次寫入就吃掉全部餘裕。

### 還沒解決的兩件事(跟這條路無關,但更重要)

1. **檔案會消失。** 關檔不提交目錄項,拔電池後最後寫的那個檔案會不見 ——
   而那永遠是 `.CSV`。實測:602,051 B 的完整檔案,拔電池後 `dir` 看不到、開檔回 0。
   線索:`LmountMcSync__v0 @ 0xC034DE90`、字串 `HasSyncedMedia`。
   **這是這條線的初衷(意外關機不掉資料),優先度最高。**
2. **停止時的爆發。** 停止路徑約 72 次卡片操作(32 次讀回 + 40 次寫),
   落在相機收尾片段的同一刻。

   **但證據沒有指向它。** 那晚五段錄影裡只有一段在停止時卡住(錄影狀態機停在
   `movwrite`、LED 一直亮、收音表沒反應、關機顯示「圖像處理中」只能拔電池)——
   而那**正好是唯一 daemon 連著的那一段**,而且錄影前才用 memprobe 打了 224 個
   標記。其餘四段 daemon 都斷開,都沒事。

   一次不算證明,但方向是清楚的,而且記憶裡本來就有 `daemon-blocks-recording`。

   **已做一半(2026-08-27):** 寫入那一半降下來了。文字緩衝原本借用 `O_BUF_B`
   —— 十六 KB,所以每十五 KB 就要落盤一次,一段錄影四十次。改成用池的
   `+0x20000`(256 KB,錄影已經結束,而且那塊驗證過撐得過錄影)之後:

   | | 之前 | 之後 |
   |---|---|---|
   | 停止路徑 | 1.056 s | **0.515 s** |
   | `.CSV` 寫入 | ~40 次 | **3 次** |
   | 掉包 | 0 | 0 |
   | 正確性 | 逐位元組相同 | **30,539 行逐位元組相同** |

   **還沒做的另一半:讀取。** 停止時仍然一個區塊讀兩次(表頭 + 酬載),16 個區塊 = 32 次。
   用韌體的慣用法(配一塊夠寬的緩衝、一次讀完、看 `actual`)可以變成 1 次 ——
   15 秒的 `.GYR` 才 250 KB,而池裡有 896 KB。長片段要處理讀不完的情況。

   **兩件事分開:**
   - **測 daemon** —— 連著 daemon 錄一段。又卡住的話,規則要寫進工具裡
     (daemon 偵測到錄影就閉嘴),而不是靠人記得。代價是可能拔一次電池。
   - **不管怎樣都減少爆發** —— 關完 `.GYR` 之後等兩三秒再做 gcsv,讓相機先收完尾。
     改動很小,而且現在有 `S_STOP_T0`/`S_STOP_T1` 可以量。

嘗試的程式碼保留在工作目錄外(`logger.S.live-final`),不進版控。
